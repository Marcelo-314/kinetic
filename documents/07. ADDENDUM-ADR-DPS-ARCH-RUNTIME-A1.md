

# ADDENDUM-ADR-DPS-ARCH-RUNTIME-A1

**Título:** Hexagonal Architecture, Explicit State Machine, and Concurrency Discipline
**Versión:** v0.1-draft
**Estado:** Draft
**Aplica sobre:**

* ADR-DPS-ASYNC-RUNTIME-001
* ADR-DPS-PERSISTENCE-002
* ADR-DPS-FAILURE-POLICY-003

**Ámbito:** Document Processing Service

## 1. Propósito

Este addendum fija tres condiciones técnicas obligatorias para la implementación:

1. **arquitectura hexagonal estricta**,
2. **máquina de estados propia, sin framework dedicado**,
3. **disciplina explícita de concurrencia y trabajo asíncrono**.

La motivación es directa: el challenge pone peso fuerte en arquitectura, concurrencia, API y manejo de errores, además de exigir procesamiento asíncrono real y lifecycle observable. 

---

## 2. Decisión 1 — Arquitectura hexagonal estricta

### 2.1. Decisión

La implementación DEBE seguir una **arquitectura hexagonal**.

### 2.2. Regla de partición

El sistema DEBE separarse, como mínimo, en estos planos:

* **dominio**
* **aplicación**
* **adapters de entrada**
* **adapters de salida**
* **bootstrap/configuración**

### 2.3. Dominio

El dominio DEBE contener únicamente:

* agregado `Process`
* estados y commands
* reglas de transición
* políticas
* invariantes
* eventos y resultados de transición

El dominio NO DEBE depender de:

* Spring
* JPA
* HTTP
* DTOs de API
* frameworks de scheduling

### 2.4. Aplicación

La capa de aplicación DEBE contener:

* casos de uso / command handlers
* query handlers
* coordinación transaccional
* uso de puertos
* orquestación entre dominio y adapters

### 2.5. Adapters de entrada

Ejemplos:

* REST controllers
* disparadores de scheduler

### 2.6. Adapters de salida

Ejemplos:

* persistencia
* filesystem
* runtime executor
* logging estructurado

### 2.7. Regla fuerte

Spring DEBE usarse como framework de composición y adapters, NO como dueño del dominio.

---

## 3. Decisión 2 — Máquina de estados propia

### 3.1. Decisión

La implementación NO DEBE usar Spring State Machine.

### 3.2. Decisión

La máquina de estados DEBE implementarse en Java 21 usando:

* `sealed interfaces`
* `record` cuando aplique
* `pattern matching`
* un motor de transición explícito

### 3.3. Modelo recomendado

#### Estados

Debe existir una representación sellada del estado del proceso, por ejemplo:

* `Pending`
* `Running`
* `Paused`
* `Completed`
* `Failed`
* `Stopped`

#### Commands

Debe existir una representación sellada de los commands, distinguiendo al menos:

* commands externos
* commands internos de runtime

#### Motor

Debe existir un `TransitionEngine` puro que reciba:

* agregado actual
* command
* contexto mínimo necesario

y devuelva:

* nuevo estado lógico,
* eventos,
* efectos declarativos.

### 3.4. Regla fuerte

La lógica de transición NO DEBE vivir en controllers, entidades JPA ni servicios Spring con conocimiento ad hoc del lifecycle.

### 3.5. Posición sobre patrón State

Este addendum adopta la siguiente postura:

* **sí** al patrón State en sentido conceptual,
* **no** al uso obligatorio del patrón GoF literal con una clase comportamental por estado.

La implementación preferida es una **state machine explícita y algebraica**, no una frameworkizada.

---

## 4. Decisión 3 — Runtime asíncrono explícito

### 4.1. Decisión

El trabajo asíncrono DEBE implementarse mediante un **runtime explícito**, no delegarse a `@Async` ni a cadenas opacas de futures como mecanismo principal.

### 4.2. Componentes mínimos del runtime

La implementación DEBE contar con:

* un **dispatcher/scheduler**
* un **mecanismo de claim o lease por proceso**
* uno o más **workers**
* chequeo explícito de flags de control (`pause` / `stop`)

### 4.3. Regla de single-flight

Para un mismo `process_id`, SOLO PUEDE existir una ejecución activa a la vez.

### 4.4. Regla de concurrencia entre procesos

El sistema PUEDE ejecutar múltiples procesos en paralelo, con un límite explícito de concurrencia configurable.

### 4.5. Regla dentro de un proceso

Dentro de un mismo proceso, los documentos DEBEN procesarse secuencialmente en esta versión.

---

## 5. Estrategia de hilos

### 5.1. Decisión

La implementación PUEDE usar **virtual threads de Java 21** para los workers.

### 5.2. Restricción

El uso de virtual threads NO IMPLICA concurrencia ilimitada.

### 5.3. Regla

Debe existir un límite explícito de procesos concurrentes, por ejemplo mediante:

* semáforo,
* scheduler acotado,
* o estrategia equivalente.

### 5.4. Justificación

Los virtual threads ayudan con el costo del bloqueo, pero NO resuelven por sí mismos:

* single-flight,
* condiciones de carrera,
* precedencia de terminalidad,
* consistencia del dominio.

---

## 6. Disciplina de mutabilidad

### 6.1. Decisión

El dominio DEBE modelarse de manera predominantemente inmutable.

### 6.2. Regla

Se consideran inmutables o close-once, conceptualmente:

* estados
* commands
* resultados de transición
* eventos
* snapshots leídos del dominio
* evidencia documental cerrada
* snapshots de resultados

### 6.3. Mutabilidad permitida

La mutabilidad controlada se concentra en:

* registros persistidos de estado actual
* flags de control
* leases/claims
* progreso actual
* referencias al snapshot vigente

### 6.4. Regla fuerte

El sistema NO DEBE depender de memoria compartida mutable en RAM como fuente de verdad del lifecycle.

---

## 7. Transacciones y boundaries

### 7.1. Decisión

La implementación NO DEBE mantener transacciones abiertas durante el análisis completo de un documento.

### 7.2. Regla operativa

El procesamiento documental DEBE separarse en tres fases:

#### Fase A — preparación transaccional corta

* reclamar proceso
* seleccionar documento
* marcar `PROCESSING`

#### Fase B — trabajo fuera de transacción

* leer archivo
* analizar contenido
* calcular métricas y summary

#### Fase C — cierre transaccional corto

* cerrar documento como `PROCESSED` o `FAILED`
* actualizar progreso
* emitir snapshot parcial si corresponde
* reevaluar terminalidad

### 7.3. Justificación

Esto reduce:

* contención,
* duración de locks,
* riesgo de inconsistencias por transacciones largas.

---

## 8. Claim / lease por proceso

### 8.1. Decisión

La ejecución de un proceso DEBE estar protegida por un mecanismo de **claim o lease**.

### 8.2. Requisitos mínimos del claim

El mecanismo debe permitir:

* reclamar un proceso elegible,
* identificar dueño temporal de ejecución,
* expirar o renovarse,
* evitar doble ejecución concurrente del mismo proceso.

### 8.3. Recuperación

Si el proceso queda reclamado por una ejecución caída o abandonada, el sistema DEBE poder recuperarlo mediante expiración del lease o mecanismo equivalente.

---

## 9. Condiciones de carrera normativas

Este addendum fija las carreras relevantes que la implementación DEBE resolver correctamente.

### 9.1. Doble authorize

Solo una transición puede ganar.
La otra DEBE fallar por conflicto de versión o transición.

### 9.2. Pause y stop concurrentes

La precedencia canónica entre señales de control será:

```text id="e3dazg"
STOP > PAUSE
```

### 9.3. Stop al cerrar último documento

Se fija la siguiente precedencia de convergencia terminal:

```text id="qfcrkg"
FAILED > STOPPED > COMPLETED > PAUSED
```

### 9.4. Justificación de esa precedencia

* un fallo terminal real no debe quedar oculto por un stop pendiente;
* un stop pendiente debe prevalecer sobre completion si ambos compiten al mismo checkpoint;
* pausa nunca debe prevalecer sobre terminalidad.

---

## 10. Reglas adicionales sobre quietud

### 10.1.

Si `status = PAUSED`, NO DEBE existir documento en `PROCESSING`.

### 10.2.

Si `status = STOPPED`, NO DEBE existir documento en `PROCESSING`.

### 10.3.

Si `status = COMPLETED`, NO DEBE quedar trabajo documental pendiente.

### 10.4.

Si `status = FAILED`, NO DEBE iniciarse nuevo trabajo documental.

---

## 11. Control de concurrencia del agregado

### 11.1. Decisión

`Process` DEBE protegerse con control de concurrencia optimista basado en `version`.

### 11.2. Alcance

Esta protección aplica especialmente a:

* authorize
* pause
* resume
* stop
* completion
* failure
* finalización por stop

### 11.3. Complemento

El optimistic locking NO reemplaza el claim/lease; ambos mecanismos son complementarios.

---

## 12. Estructura arquitectónica recomendada

Este addendum recomienda, como mínimo, una estructura lógica equivalente a:

```text id="5ow45t"
dps-domain
dps-application
dps-adapters-in-web
dps-adapters-out-persistence
dps-adapters-out-filesystem
dps-adapters-out-runtime
dps-bootstrap
```

Puede implementarse como multi-módulo real o como monolito modularizado por paquetes, pero la separación conceptual DEBE mantenerse.

---

## 13. Restricciones negativas

La implementación NO DEBE:

* poner lógica de lifecycle en controllers,
* usar entidades JPA como modelo de dominio canónico,
* usar `@Async` como sustituto del runtime modelado,
* usar shared mutable maps en memoria como fuente de verdad,
* permitir más de un documento en `PROCESSING` por proceso en esta versión,
* interpretar aceptación de command como convergencia estable inmediata.

---

## 14. Consecuencias sobre el SDD

El SDD deberá bajar explícitamente:

* los módulos/paquetes hexagonales,
* las sealed interfaces del lifecycle,
* el `TransitionEngine`,
* los puertos de repositorio y runtime,
* el mecanismo de claim/lease,
* la estrategia de ejecución con virtual threads acotados,
* las fases transaccionales cortas,
* y la precedencia terminal fijada aquí.

---

Este addendum queda aprobado como restricción técnica de implementación.

## 16. Decisión adicional — Spring Boot como framework de composición

### 16.1. Decisión

La implementación **DEBE** realizarse como un servicio **Spring Boot**.

### 16.2. Alcance de la decisión

Spring Boot se utilizará para:

* bootstrap y configuración,
* composición de dependencias,
* adapters web,
* transacciones,
* persistencia,
* scheduling/disparadores,
* observabilidad y configuración operativa del servicio.

### 16.3. Restricción

Spring Boot **NO DEBE** convertirse en el dueño del dominio ni del lifecycle del proceso.

### 16.4. Consecuencia

El dominio, la máquina de estados, los commands, las policies y el runtime modelado seguirán siendo responsabilidad de la arquitectura propia del servicio.

### 16.5. Justificación

Esta decisión preserva el enfoque hexagonal ya fijado: Spring actúa como framework de composición y adapters, mientras que la semántica de dominio queda desacoplada del framework.

---

## 17. Decisión adicional — No uso de Spring Batch

### 17.1. Decisión

La implementación **NO DEBE** utilizar **Spring Batch**.

### 17.2. Alcance de la decisión

El servicio sí podrá implementarse sobre Spring Boot, pero el procesamiento por lotes del dominio será responsabilidad del runtime explícito del servicio y no del modelo técnico `Job/Step` de Spring Batch.

### 17.3. Justificación funcional

El challenge exige procesamiento por lotes, asincronía real, persistencia de estados, resultados y logs, además de control por API sobre procesos identificables. No exige el uso de Spring Batch como framework. 

### 17.4. Justificación técnica

El uso de Spring Batch introduciría una segunda semántica de lifecycle (`Job`, `Step`, `JobExecution`, `BatchStatus`, `ExitStatus`) superpuesta al lifecycle de dominio ya definido (`PENDING`, `RUNNING`, `PAUSED`, `COMPLETED`, `FAILED`, `STOPPED`). Esa superposición aumentaría complejidad técnica y conceptual sin beneficio proporcional para el alcance del proyecto. El challenge pide comportamiento batch, no una tecnología batch específica. 

### 17.5. Consecuencia

La planificación por lotes, la ejecución asíncrona, los checkpoints seguros, la pausa, la reanudación, la detención y la consolidación de resultados serán responsabilidad del runtime explícito definido por la arquitectura del servicio.

### 17.6. Restricción adicional

La implementación **NO DEBE** modelar el lifecycle del proceso en términos de artefactos propios de Spring Batch si eso compromete o duplica el lifecycle de dominio ya aprobado.
