# Chronicle - Incremento 02 State Machine

**Fecha:** 2026-04-19  
**Estado:** Implementado  
**Objetivo del incremento:** implementar el dominio puro del lifecycle con máquina de estados propia y tests exhaustivos del `TransitionEngine`, corrigiendo además los puntos pendientes del incremento 01.

* RFC de lifecycle y semántica pública
* PDR de runtime y commands
* addendum arquitectónico que exige máquina de estados propia
* restricciones de hexagonal architecture y dominio puro

## 3. Dominio puro implementado

Se incorporó la base del dominio puro en la capa `domain`.

### 3.1. Estados del proceso

Se implementó `ProcessState` como jerarquía sellada con los estados:

* `Pending`
* `Running`
* `Paused`
* `Completed`
* `Failed`
* `Stopped`

La jerarquía usa Java 21 con `sealed interface` y `record`.

### 3.2. Commands del proceso

Se implementó `ProcessCommand` como jerarquía sellada con los commands mínimos necesarios para este incremento:

* `AuthorizeProcess`
* `PauseProcess`
* `ResumeProcess`
* `StopProcess`
* `ResolveCheckpoint`

`ResolveCheckpoint` se introdujo como command interno del dominio para modelar la convergencia en checkpoint seguro sin traer todavía runtime real.

### 3.3. Aggregate mínimo

Se implementó un `ProcessAggregate` mínimo con:

* `processId`
* `state`
* `version`
* `pauseRequested`
* `stopRequested`

Este agregado es suficiente para expresar:

* estado observable actual
* intenciones de control
* resolución posterior en checkpoint

### 3.4. Contexto y resultado de transición

Se implementaron:

* `TransitionContext`
* `TransitionResult`

`TransitionContext` contiene solo la información mínima necesaria para este incremento:

* `failureDetected`
* `workCompleted`

`TransitionResult` devuelve el nuevo agregado y el command aplicado.

### 3.5. Error explícito de transición inválida

Se implementó:

* `InvalidTransitionException`

Esto permite rechazar transiciones inválidas de forma explícita, como exige el RFC.

## 4. TransitionEngine implementado

Se implementó:

* `TransitionEngine`
* `DefaultTransitionEngine`

El motor es:

* puro
* sin Spring
* sin persistencia
* sin IO
* sin dependencias de framework

## 5. Semántica modelada en el motor

El motor implementa estas reglas:

### 5.1. Transiciones válidas

* `PENDING + AuthorizeProcess -> RUNNING`
* `RUNNING + PauseProcess -> RUNNING` con `pauseRequested = true`
* `PAUSED + ResumeProcess -> RUNNING`
* `PENDING + StopProcess -> STOPPED`
* `RUNNING + StopProcess -> RUNNING` con `stopRequested = true`
* `PAUSED + StopProcess -> STOPPED`

### 5.2. Resolución en checkpoint

Para el estado `RUNNING`, `ResolveCheckpoint` aplica la precedencia:

```text
FAILED > STOPPED > COMPLETED > PAUSED
```

En concreto:

1. si `failureDetected = true` -> `FAILED`
2. si `stopRequested = true` -> `STOPPED`
3. si `workCompleted = true` -> `COMPLETED`
4. si `pauseRequested = true` -> `PAUSED`
5. si no hay nada que resolver -> permanece en `RUNNING`

### 5.3. Precedencia de señales de control

También quedó modelada:

```text
STOP > PAUSE
```

Si ambas señales están activas al llegar al checkpoint, el proceso converge a `STOPPED`.

### 5.4. Estados terminales absorbentes

Los estados:

* `COMPLETED`
* `FAILED`
* `STOPPED`

son absorbentes y rechazan nuevos commands.

## 6. Tests implementados

Se agregó la suite:

* `DefaultTransitionEngineTest`

La suite cubre:

* authorize válido desde pending
* authorize inválido desde running y terminales
* pause válido desde running
* pause inválido desde pending, paused y terminales
* resume válido desde paused
* resume inválido desde running, pending y terminales
* stop válido desde pending, running y paused
* stop inválido desde terminales
* absorbencia terminal
* precedencia `STOP > PAUSE`
* precedencia `FAILED > STOPPED > COMPLETED > PAUSED`
* permanencia en `RUNNING` cuando el checkpoint no resuelve nada

* runtime dispatcher
* lease manager
* workers
* adapters funcionales de infraestructura

Tampoco se incorporaron anotaciones Spring/JPA en el dominio.
