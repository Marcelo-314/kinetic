
# PDR-DPS-RUNTIME-CQRS-002

**Título:** Runtime and Command/Query Processing
**Versión:** v0.1-draft
**Estado:** Draft
**Predecesores:**

* RFC-DPS-LIFECYCLE-API-001
* PDR-DPS-DOMAIN-OWNERSHIP-001

**Ámbito:** Document Processing Service

## 1. Propósito

Este PDR fija el comportamiento operativo del sistema a partir del dominio ya definido. Su objetivo es dejar explícito:

* qué **commands** existen,
* qué **queries** existen,
* qué precondiciones y postcondiciones tiene cada operación,
* qué componente ejecuta cada operación,
* cómo se articula el runtime asíncrono con el lifecycle del proceso,
* y cómo se preserva la consistencia entre estado, progreso, evidencia documental y resultados.

El challenge exige procesamiento asíncrono real, manejo concurrente de estado, persistencia de estados/resultados/logs y una API capaz de iniciar, detener, consultar estado, listar y devolver resultados. Por eso este PDR trata al sistema como un **servicio de jobs con control explícito**, no como una simple API CRUD. 

---

## 2. Relación con artefactos previos

Este PDR **no redefine**:

* el conjunto de estados,
* la semántica de `PENDING/RUNNING/PAUSED/COMPLETED/FAILED/STOPPED`,
* la semántica `NONE/PARTIAL/FINAL`,
* el modelo de objetos y ownership.

Eso ya quedó fijado.

Este PDR **sí define**:

* el catálogo de commands y queries,
* el flujo operativo de ejecución,
* la relación entre commands externos e internos,
* las reglas de convergencia del runtime,
* los puntos de sincronización relevantes,
* la política de lectura de proyecciones.

---

## 3. Principio rector

El sistema DEBE seguir esta regla:

> **Los commands expresan intención de cambio. Las queries expresan observación.**

Corolarios:

### 3.1.

Una query NO DEBE mutar estado.

### 3.2.

Un command PUEDE ser aceptado antes de que la convergencia estable sea visible en el lifecycle.

### 3.3.

La API externa NO DEBE asumir instantaneidad física del runtime cuando el sistema aún está convergiendo hacia un checkpoint seguro.

Esto es especialmente importante para `pause` y `stop`, dado el carácter asíncrono real exigido por el challenge. 

---

## 4. Clasificación de operaciones

Este PDR clasifica las operaciones en cuatro grupos:

### 4.1. Commands públicos

Operaciones invocadas externamente por la API.

### 4.2. Commands internos

Operaciones emitidas por el runtime o la orquestación para cerrar trabajo, fijar terminalidad o producir resultados.

### 4.3. Queries públicas

Lecturas expuestas por API.

### 4.4. Queries internas

Lecturas auxiliares del runtime y del agregado, no necesariamente expuestas.

---

# 5. Commands públicos

## 5.1. `CreateProcess`

### Rol

Crear una nueva corrida con plan congelado, dejándola en `PENDING`.

### Iniciador

API Layer

### Ejecuta

Process Orchestrator

### Input conceptual

* `objective`
* `source_folder`
* `selection_mode`
* `selected_files`
* `batch_size`
* `summary_policy`
* `failure_policy`
* `authorization_required`

### Precondiciones

* request válida;
* carpeta fuente válida;
* selección consistente;
* cardinalidad del plan resoluble;
* `batch_size > 0`.

### Efectos

* crea `Process`;
* crea `ProcessPlan`;
* crea `AuthorizationInfo`;
* inicializa `ProgressSnapshot`;
* registra `PROCESS_CREATED`.

### Postcondiciones

* existe `process_id`;
* `status = PENDING`;
* `result_kind = NONE`.

### Rechazos

* request inválida;
* plan semánticamente inviable.

### Observación

`CreateProcess` NO DEBE iniciar procesamiento documental.

---

## 5.2. `AuthorizeProcess`

### Rol

Conceder autorización operacional y despachar el proceso al runtime.

### Iniciador

API Layer

### Ejecuta

Authorization Service + Process Orchestrator + Runtime Scheduler

### Input

* `process_id`

### Precondiciones

* proceso existente;
* `status = PENDING`;
* autorización aún no concedida;
* proceso no terminal.

### Efectos

* `authorization_state -> AUTHORIZED`;
* `Process.status -> RUNNING`;
* fija `ProgressSnapshot.started_at`;
* materializa trabajo inicial:

  * crea `DocumentExecution` pendientes,
  * crea `BatchExecution` planificados si aplica;
* registra `PROCESS_AUTHORIZED`.

### Postcondiciones

* proceso observable como `RUNNING`;
* runtime elegible para consumir lotes.

### Rechazos

* proceso inexistente;
* transición inválida.

---

## 5.3. `PauseProcess`

### Rol

Solicitar suspensión ordenada de un proceso activo.

### Iniciador

API Layer

### Ejecuta

Process Orchestrator registra intención; Runtime Scheduler converge

### Input

* `process_id`

### Precondiciones

* proceso existente;
* `status = RUNNING`.

### Efectos inmediatos

* `ExecutionControlFlags.pause_requested = true`
* registra `PAUSE_REQUESTED`

### Efectos diferidos

* al alcanzar checkpoint seguro:

  * `Process.status -> PAUSED`
  * progreso queda estable
  * registra `PROCESS_PAUSED`

### Postcondición semántica

La pausa queda aceptada aunque la transición física a `PAUSED` pueda demorarse.

### Rechazos

* proceso inexistente;
* estado distinto de `RUNNING`.

---

## 5.4. `ResumeProcess`

### Rol

Reanudar un proceso previamente pausado.

### Iniciador

API Layer

### Ejecuta

Process Orchestrator + Runtime Scheduler

### Input

* `process_id`

### Precondiciones

* proceso existente;
* `status = PAUSED`.

### Efectos

* limpia intención de pausa;
* `Process.status -> RUNNING`;
* registra `PROCESS_RESUMED`.

### Postcondiciones

* runtime vuelve a estar habilitado para consumir trabajo.

### Rechazos

* inexistencia;
* transición inválida.

---

## 5.5. `StopProcess`

### Rol

Detener administrativamente un proceso.

### Iniciador

API Layer

### Ejecuta

Process Orchestrator registra intención; Runtime Scheduler converge; Process Orchestrator fija terminalidad

### Input

* `process_id`

### Precondiciones

* proceso existente;
* `status ∈ {PENDING, RUNNING, PAUSED}`.

### Efectos por estado

#### Desde `PENDING`

* `Process.status -> STOPPED`
* crea `TerminalInfo`
* registra `PROCESS_STOPPED`

#### Desde `RUNNING`

* `ExecutionControlFlags.stop_requested = true`
* registra `STOP_REQUESTED`
* convergencia diferida a `STOPPED` en checkpoint seguro

#### Desde `PAUSED`

* `Process.status -> STOPPED`
* crea `TerminalInfo`
* registra `PROCESS_STOPPED`

### Rechazos

* inexistencia;
* estado terminal;
* transición inválida.

### Regla fuerte

`StopProcess` NUNCA DEBE degenerar en `FAILED`.

---

# 6. Commands internos

Estos commands no requieren exposición HTTP. Son parte del comportamiento del runtime.

## 6.1. `MaterializeProcessWork`

### Rol

Instanciar el trabajo operativo a partir del plan.

### Ejecuta

Runtime Scheduler + Batch Planner

### Precondiciones

* proceso autorizado;
* plan válido y congelado.

### Efectos

* crea `DocumentExecution` para todos los documentos del plan;
* asigna `batch_index`;
* opcionalmente crea `BatchExecution`.

### Postcondición

Existe trabajo operacional concreto para el runtime.

---

## 6.2. `DispatchNextBatch`

### Rol

Seleccionar el siguiente batch elegible y activarlo.

### Ejecuta

Runtime Scheduler

### Precondiciones

* `status = RUNNING`;
* no hay `pause_requested`;
* no hay `stop_requested`;
* existe batch o documento pendiente.

### Efectos

* marca batch como activo;
* marca documentos del lote como `PROCESSING`;
* registra `BATCH_STARTED`.

---

## 6.3. `RecordDocumentSuccess`

### Rol

Cerrar exitosamente un documento.

### Ejecuta

Document Analyzer emite evidencia; Runtime Scheduler consolida progreso

### Input

* `process_id`
* `document_execution_id`
* `word_count`
* `line_count`
* `character_count`
* `most_frequent_words`
* `summary`
* `summary_method`

### Precondiciones

* documento existente;
* documento en `PROCESSING`;
* proceso no terminal.

### Efectos

* `document_status -> PROCESSED`
* fija métricas y summary
* actualiza progreso
* registra `DOCUMENT_PROCESSED`

### Postcondiciones

El documento pasa a ser evidencia elegible para agregación.

---

## 6.4. `RecordDocumentFailure`

### Rol

Cerrar un documento como fallido.

### Ejecuta

Document Analyzer / Runtime Scheduler

### Input

* `process_id`
* `document_execution_id`
* `error_code`
* `error_message`

### Precondiciones

* documento existente;
* documento en `PROCESSING`;
* proceso no terminal.

### Efectos

* `document_status -> FAILED`
* fija causalidad documental
* actualiza progreso
* registra `DOCUMENT_FAILED`

### Postcondiciones

El documento NO es elegible para agregados de éxito.

---

## 6.5. `CloseBatch`

### Rol

Cerrar el lote activo luego de procesar todos sus documentos.

### Ejecuta

Runtime Scheduler

### Precondiciones

* batch activo;
* todos sus documentos cerrados.

### Efectos

* `batch_status -> COMPLETED` o equivalente final del lote
* registra `BATCH_FINISHED`

---

## 6.6. `SnapshotPartialResult`

### Rol

Emitir snapshot analítico parcial del proceso.

### Ejecuta

Result Aggregator

### Precondiciones

* existe al menos un `DocumentExecution` en `PROCESSED`.

### Efectos

* crea `ProcessResult` con `result_kind = PARTIAL`
* actualiza referencia al snapshot vigente
* registra `PARTIAL_RESULT_SNAPSHOTTED`

### Regla fuerte

Solo puede consolidar evidencia documental ya cerrada con éxito.

---

## 6.7. `CompleteProcess`

### Rol

Cerrar exitosamente el proceso.

### Ejecuta

Process Orchestrator

### Precondiciones

* `status = RUNNING`
* no quedan documentos pendientes según el plan y la política vigente
* no existe orden de stop aplicable
* no existe causa terminal de fallo

### Efectos

* `Process.status -> COMPLETED`
* crea `TerminalInfo`
* dispara snapshot final
* registra `PROCESS_COMPLETED`

### Postcondiciones

* `result_kind = FINAL`
* cobertura total del plan

---

## 6.8. `FailProcess`

### Rol

Cerrar el proceso por error terminal.

### Ejecuta

Process Orchestrator

### Precondiciones

* proceso aún no terminal
* existe causa no recuperable

### Efectos

* `Process.status -> FAILED`
* crea `TerminalInfo`
* opcionalmente emite snapshot parcial terminal
* registra `PROCESS_FAILED`

---

## 6.9. `FinalizeStoppedProcess`

### Rol

Materializar terminalidad estable por stop aceptado.

### Ejecuta

Process Orchestrator

### Precondiciones

* `stop_requested = true`
* runtime ya alcanzó checkpoint seguro o el proceso estaba quieto

### Efectos

* `Process.status -> STOPPED`
* crea `TerminalInfo`
* emite snapshot parcial terminal si corresponde
* registra `PROCESS_STOPPED`

---

# 7. Queries públicas

## 7.1. `GetProcessStatus`

### Rol

Devolver la vista operativa canónica del proceso.

### Ejecuta

API Layer leyendo proyección operacional

### Fuente de lectura

* `Process`
* `AuthorizationInfo`
* `ProgressSnapshot`
* `TerminalInfo`

### Regla fuerte

NO DEBE recalcular analítica ni inferir terminalidad por fuera del agregado.

---

## 7.2. `ListProcesses`

### Rol

Devolver catálogo resumido de procesos.

### Fuente de lectura

* `Process`
* resumen de `ProgressSnapshot`
* `result_kind` vigente

### Reglas

* paginable
* filtrable por estado
* orientado a observación, no a detalle documental

---

## 7.3. `GetProcessResults`

### Rol

Devolver la proyección analítica vigente del proceso.

### Fuente de lectura

* `ProcessResult`
* `DocumentExecution`
* `TerminalInfo` si aplica

### Regla fuerte

Debe leer snapshots persistidos, no reconstruir todo al vuelo salvo decisión explícita del ADR de persistencia.

---

## 7.4. `GetProcessActivity` (opcional)

### Rol

Exponer el historial operativo del proceso.

### Fuente de lectura

* `ActivityLogEntry`

### Justificación

Aunque no es obligatorio por el challenge como endpoint, sí es coherente con su exigencia de activity logs persistidos. 

---

# 8. Queries internas

## 8.1. `LoadRunnableProcess`

Retorna un proceso elegible para continuar ejecución.

## 8.2. `LoadNextPendingBatch`

Retorna el siguiente batch o conjunto documental pendiente.

## 8.3. `LoadProcessedDocumentsForAggregation`

Retorna evidencia analítica lista para agregación.

## 8.4. `LoadCurrentControlFlags`

Retorna señales vigentes de pausa/stop.

Estas queries pertenecen al runtime y NO forman parte del contrato público.

---

# 9. State machine operacional

El RFC ya fijó las transiciones válidas. Este PDR define cómo se recorren operacionalmente.

## 9.1. Camino nominal exitoso

1. `CreateProcess`
2. `AuthorizeProcess`
3. `MaterializeProcessWork`
4. `DispatchNextBatch`
5. `RecordDocumentSuccess` / `CloseBatch`
6. `SnapshotPartialResult` (opcionalmente varias veces)
7. repetición de 4-6 hasta agotar trabajo
8. `CompleteProcess`
9. `GetProcessResults -> FINAL`

## 9.2. Camino con pausa

1. proceso en `RUNNING`
2. `PauseProcess`
3. runtime completa checkpoint seguro
4. `Process.status -> PAUSED`
5. `ResumeProcess`
6. `Process.status -> RUNNING`

## 9.3. Camino con stop

1. proceso en `PENDING`, `RUNNING` o `PAUSED`
2. `StopProcess`
3. si estaba `RUNNING`, convergencia a checkpoint
4. `FinalizeStoppedProcess`
5. `GetProcessResults -> PARTIAL` o `NONE` según evidencia

## 9.4. Camino de fallo

1. documento o runtime reporta causa terminal
2. `FailProcess`
3. proceso queda `FAILED`
4. `GetProcessResults -> PARTIAL`

# 10. Reglas de checkpoint y convergencia

Este PDR todavía no fija la granularidad exacta del checkpoint; eso quedará cerrado por ADR. Pero sí fija reglas normativas mínimas.

## 10.1.

`pause` y `stop` PUEDEN requerir checkpoint seguro.

## 10.2.

Mientras no se alcance ese checkpoint, el proceso PUEDE seguir observable como `RUNNING`.

## 10.3.

El sistema NO DEBE exponer `PAUSED` ni `STOPPED` antes de que la convergencia sea estable.

## 10.4.

El checkpoint seguro DEBE preservar consistencia entre:

* estado del proceso,
* progreso,
* documentos cerrados,
* snapshot analítico vigente.

---

# 11. Política de agregación analítica

## 11.1. Regla base

La agregación DEBE realizarse sobre documentos `PROCESSED`.

## 11.2.

Los documentos `FAILED` PUEDEN aparecer en detalle documental, pero NO DEBEN sumarse a métricas agregadas de éxito.

## 11.3.

`SnapshotPartialResult` PUEDE emitirse:

* al cerrar cada documento,
* al cerrar cada batch,
* al alcanzar hitos configurables.

La decisión exacta se cierra en ADR de persistencia/runtime.

## 11.4.

`FINAL_RESULT_SNAPSHOTTED` SOLO puede emitirse tras `CompleteProcess`.

---

# 12. Política de error y escalamiento

Este PDR todavía no cierra la estrategia definitiva de fallo; eso será ADR específico. Pero sí fija una estructura de escalamiento.

## 12.1. Fallo documental

Un error localizado en un documento produce `RecordDocumentFailure`.

## 12.2. Fallo de proceso

Un error de proceso produce `FailProcess`.

## 12.3. Regla de escalamiento

El paso de fallo documental a fallo terminal de proceso depende de `failure_policy`.

## 12.4.

La API NO DEBE colapsar automáticamente un fallo documental aislado a `FAILED` si la política vigente es tolerante.

---

# 13. Política de lectura de resultados

## 13.1.

`GetProcessResults` DEBE comportarse así:

* `PENDING -> NONE`
* `RUNNING -> PARTIAL` si hay evidencia; ventana inicial puede ser `NONE`
* `PAUSED -> PARTIAL`
* `STOPPED -> PARTIAL` o `NONE` si no hubo trabajo
* `FAILED -> PARTIAL`
* `COMPLETED -> FINAL`

## 13.2.

`GetProcessResults` NO DEBE inventar consolidación final antes de `COMPLETED`.

## 13.3.

El `global_summary` solo es canónico en `FINAL`.

# 14. Matriz de admisibilidad de commands

| Estado actual |                    create | authorize | pause | resume | stop |
| ------------- | ------------------------: | --------: | ----: | -----: | ---: |
| inexistente   |                        sí |        no |    no |     no |   no |
| `PENDING`     | no sobre el mismo proceso |        sí |    no |     no |   sí |
| `RUNNING`     | no sobre el mismo proceso |        no |    sí |     no |   sí |
| `PAUSED`      | no sobre el mismo proceso |        no |    no |     sí |   sí |
| `COMPLETED`   | no sobre el mismo proceso |        no |    no |     no |   no |
| `FAILED`      | no sobre el mismo proceso |        no |    no |     no |   no |
| `STOPPED`     | no sobre el mismo proceso |        no |    no |     no |   no |

Las operaciones inválidas DEBEN devolver conflicto de transición.

# 15. Matriz de ownership operativo

| Operación                | Origen                | Ejecuta                                | Muta principal                                                    |
| ------------------------ | --------------------- | -------------------------------------- | ----------------------------------------------------------------- |
| `CreateProcess`          | API                   | Process Orchestrator                   | `Process`, `ProcessPlan`, `AuthorizationInfo`, `ProgressSnapshot` |
| `AuthorizeProcess`       | API                   | Authorization + Orchestrator + Runtime | `AuthorizationInfo`, `Process`, runtime materialization           |
| `PauseProcess`           | API                   | Orchestrator + Runtime                 | `ExecutionControlFlags`, luego `Process.status`                   |
| `ResumeProcess`          | API                   | Orchestrator + Runtime                 | `ExecutionControlFlags`, `Process.status`                         |
| `StopProcess`            | API                   | Orchestrator + Runtime                 | `ExecutionControlFlags`, luego `Process.status`                   |
| `RecordDocumentSuccess`  | Runtime/Analyzer      | Analyzer + Runtime                     | `DocumentExecution`, `ProgressSnapshot`                           |
| `RecordDocumentFailure`  | Runtime/Analyzer      | Analyzer + Runtime                     | `DocumentExecution`, `ProgressSnapshot`                           |
| `SnapshotPartialResult`  | Runtime/Results       | Result Aggregator                      | `ProcessResult`                                                   |
| `CompleteProcess`        | Runtime/Orchestration | Orchestrator                           | `Process`, `TerminalInfo`, `ProcessResult`                        |
| `FailProcess`            | Runtime/Orchestration | Orchestrator                           | `Process`, `TerminalInfo`, snapshot terminal                      |
| `FinalizeStoppedProcess` | Runtime/Orchestration | Orchestrator                           | `Process`, `TerminalInfo`, snapshot terminal                      |

# 16. Secuencias mínimas canónicas

## 16.1. Secuencia `Create -> Authorize`

1. API valida request
2. Orchestrator crea proceso
3. API devuelve `201`
4. API autoriza
5. Authorization Service concede
6. Orchestrator fija `RUNNING`
7. Runtime materializa trabajo
8. API devuelve `202`

## 16.2. Secuencia `Pause`

1. API recibe pause
2. Orchestrator marca intención
3. API devuelve `202`
4. Runtime detecta intención
5. completa checkpoint
6. Orchestrator fija `PAUSED`

## 16.3. Secuencia `Stop from RUNNING`

1. API recibe stop
2. Orchestrator marca intención
3. API devuelve `202`
4. Runtime alcanza checkpoint
5. Orchestrator ejecuta `FinalizeStoppedProcess`
6. proceso queda `STOPPED`

## 16.4. Secuencia `Complete`

1. último documento se cierra
2. runtime detecta que no queda trabajo elegible
3. Orchestrator ejecuta `CompleteProcess`
4. Aggregator emite `FINAL`
5. status observable `COMPLETED`

# 17. Reglas de consistencia observable

## 17.1.

Un command aceptado NO implica necesariamente transición visible inmediata.

## 17.2.

La query `GetProcessStatus` DEBE ser consistente con el punto estable alcanzado, no con la mera intención.

## 17.3.

La query `GetProcessResults` DEBE reflejar solo snapshots ya persistidos.

## 17.4.

El runtime NO DEBE dejar al sistema en estados mixtos observables, por ejemplo:

* `status = PAUSED` con documento aún `PROCESSING` si el checkpoint prometido exige quietud,
* `status = STOPPED` sin `TerminalInfo`,
* `status = COMPLETED` con `result_kind != FINAL`.

## 18.1.

Granularidad del checkpoint seguro:

* fin de documento,
* fin de batch,
* otro.

## 18.2.

Política concreta de emisión de snapshots parciales.

## 18.3.

Mecanismo de scheduling y ejecución asíncrona.

## 18.4.

Control de concurrencia del agregado `Process`.

## 18.5.

Representación física de resultados y logs.

# 19. Dictamen

Este PDR deja estabilizado el comportamiento lógico del sistema:

* commands definidos,
* queries definidas,
* ownership operacional clara,
* flujo de runtime separado del lifecycle visible,
* consistencia entre evidencia documental, progreso y resultados.
