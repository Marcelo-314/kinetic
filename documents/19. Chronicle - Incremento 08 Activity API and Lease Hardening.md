# Chronicle - Incremento 08 Activity API and Lease Hardening

## Objetivo

Este incremento endurece el runtime frente a pérdida de lease durante el procesamiento documental y expone `GET /api/v1/processes/{process_id}/activity` con filtros y paginación mínimos, manteniendo la arquitectura hexagonal y evitando adelantar funcionalidades ajenas al foco del incremento.

## Alcance implementado

## 1. Runtime hardening ante fallo de renovación de lease

Se cerró explícitamente el comportamiento cuando la renovación del lease falla.

### Regla implementada

Si `renew(processId, ownerId, ...)` devuelve `false`, el worker deja de comportarse como dueño válido del proceso y aborta el trabajo en curso de forma segura.

### Comportamiento actual

- el documento en curso no se cierra como `PROCESSED` ni `FAILED`
- el progreso no se incrementa artificialmente
- la evidencia documental no se consolida de forma inválida
- el documento vuelve a `PENDING`
- se registra `LEASE_RENEWAL_FAILED`

### Resultado

El runtime ya no continúa silenciosamente tras perder exclusividad sobre el `process_id`.

## 2. Invariantes operativas reforzadas

Se mantuvieron y endurecieron las invariantes clave del runtime:

- no más de un worker efectivo por `process_id`
- no más de un documento `PROCESSING` por proceso
- `pause` y `stop` siguen convergiendo en checkpoint seguro
- el sistema evita estados mixtos inconsistentes cuando se pierde el lease

### Salvaguardas aplicadas

- validación explícita de un único documento `PROCESSING`
- aborto controlado si el worker pierde el lease
- preservación del checkpoint seguro al cierre documental

## 3. Activity pública

Se implementó `GET /api/v1/processes/{process_id}/activity` alineado con OpenAPI.

### Características

- controller delgado
- use case de application dedicado
- DTOs web externos separados
- `404` para proceso inexistente
- `200` con `ActivityListResponse`

### Parámetros soportados

- `from`
- `to`
- `event_type`
- `page`
- `page_size`

## 4. Query/use case de activity

Se agregó la cadena de application necesaria para exponer activity sin acoplar la web a persistencia.

### Componentes agregados

- `GetProcessActivityQuery`
- `GetProcessActivityUseCase`
- `ActivityItemView`
- `ProcessActivityView`

### Regla arquitectónica respetada

- application depende de puertos
- web depende de application
- web no consulta repositorios directamente

## 5. DTOs web de activity

Se agregaron los DTOs externos mínimos para implementar el contrato HTTP de OpenAPI:

- `ActivityItemDto`
- `ActivityListResponseDto`

El payload expuesto queda alineado con:

- `activity_id`
- `timestamp`
- `event_type`
- `event_stage`
- `message`
- `metadata`

## 6. Persistencia de activity

Se completó la persistencia de activity para soportar filtros y paginación mínimos.

### Capacidades agregadas

- búsqueda por `process_id`
- filtro por rango temporal
- filtro por `event_type`
- paginación mínima
- conteo total para la respuesta paginada
- orden consistente por `timestamp desc`

### Implementación

Se extendió el puerto `ActivityLogRepository` y se implementó la búsqueda filtrada/paginada en el adapter JPA usando `Specification` y `PageRequest`.

## 7. Alineación del modelo ActivityLogEntry

Se revisó el modelo y su persistencia para sostener coherentemente:

- `activity_id`
- `timestamp`
- `event_type`
- `event_stage`
- `message`
- `metadata`
- `correlation_id`

No se introdujo un sistema de auditoría adicional ni una infraestructura más compleja que el activity log acordado.

## 8. Qué no se implementó todavía

Se mantuvieron las restricciones de este incremento:

- no se cambió el contrato de `results` más allá de lo necesario
- no se agregaron features nuevas ajenas al hardening y a activity
- no Spring Batch
- no Spring State Machine
- no runtime en controllers
- no JPA en dominio

## 9. Tests agregados y actualizados

Se agregó cobertura específica para los requisitos de este incremento.

### Runtime hardening

- si `renew(...)` falla, el worker no continúa como si siguiera teniendo el lease
- no aparece doble procesamiento efectivo del mismo `process_id`
- se preserva la invariante de un único documento `PROCESSING`
- `pause` y `stop` siguen funcionando bajo el runtime endurecido

### Activity endpoint

- `GET /api/v1/processes/{id}/activity -> 200`
- paginación básica
- filtro por `event_type`
- filtro por `from/to`
- `404` para proceso inexistente

### Persistencia de activity

- búsqueda por `process_id`
- orden descendente esperado
- filtros aplicados correctamente
- conteo total consistente con la paginación

## Resultado

Chronicle queda ahora más robusto frente a pérdida de lease durante documentos largos: el worker aborta de forma semánticamente correcta y preserva exclusividad, progreso y evidencia.

Además, la API pública ahora expone activity con filtros y paginación mínimos, alineada con OpenAPI y desacoplada de la persistencia concreta mediante la capa application. El cambio se mantuvo incremental, limpio y revisable, sin adelantar infraestructura ni funcionalidades ajenas al objetivo del incremento.
