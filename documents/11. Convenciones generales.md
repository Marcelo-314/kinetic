
# 1. Convenciones generales

## 1.1. Prefijo de API

Se propone como contrato canónico:

```text
/api/v1
```

y como recurso principal:

```text
/processes
```

El set completo queda más limpio que la forma “verbo en path”.
Para no romper la lectura del challenge, conviene documentar **compatibilidad semántica** con sus paths originales. El enunciado publica `POST /process/start`, `POST /process/stop/{process_id}`, `GET /process/status/{process_id}`, `GET /process/list` y `GET /process/results/{process_id}`. 

## 1.2. Formato de payload

Externamente usaría **snake_case** en JSON, para quedar alineado con el ejemplo del challenge, que ya usa campos como `process_id`, `estimated_completion` y `files_processed`. 

## 1.3. Regla de asincronía

Todo command que altere el lifecycle debe interpretarse así:

* la **aceptación HTTP** y la **convergencia del proceso** no son necesariamente instantáneas;
* `pause` y `stop` pueden requerir alcanzar un punto seguro;
* `status` es la fuente de verdad de la convergencia estable.

Esto es coherente con que el challenge exige procesamiento asíncrono real y manejo concurrente de estado.

# 2. Enumeraciones canónicas

## 2.1. `process_status`

```text
PENDING
RUNNING
PAUSED
COMPLETED
FAILED
STOPPED
```

Estos estados vienen del challenge. En nuestra postura, `PENDING` significa “proceso creado pero aún no autorizado/despachado”, y `PAUSED` es operable. El enunciado enumera exactamente esos seis estados. 

## 2.2. `authorization_state`

```text
WAITING
AUTHORIZED
REJECTED
NOT_REQUIRED
```

Esto es extensión nuestra. 

## 2.3. `result_kind`

```text
NONE
PARTIAL
FINAL
```

Esto es extensión nuestra para resolver la granularidad de resultados. 

## 2.4. `document_status`

```text
PENDING
PROCESSING
PROCESSED
FAILED
SKIPPED
```

Esto también es una especificación nuestra, a nivel documental. 

## 2.5. `selection_mode`

```text
ALL_FROM_FOLDER
EXPLICIT_SELECTION
```

## 2.6. `summary_policy`

```text
EXTRACTIVE_DETERMINISTIC
```

Se deja uno solo como policy obligatoria por ahora, porque ya se tomó la postura de que el summary debe ser determinista y no generativo. 

## 2.7. `failure_policy`

```text
FAIL_FAST
TOLERATE_PARTIAL_FAILURES
```

La representación canónica resumida de un proceso debería verse así:

```json

  "status": "PENDING",
  "version": 1,
  "created_at": "2026-04-18T15:30:00Z",
  "updated_at": "2026-04-18T15:30:00Z",
  "objective": "analyze selected documents for lexical metrics and summary",
  "plan": {
    "source_folder": "/data/input",
    "selection_mode": "EXPLICIT_SELECTION",
    "selected_files": [
      "doc-01.txt",
      "doc-02.txt"
    ],
    "total_planned_files": 2,
    "batch_size": 1,
    "summary_policy": "EXTRACTIVE_DETERMINISTIC",
    "failure_policy": "TOLERATE_PARTIAL_FAILURES"
  },
  "authorization": {
    "authorization_required": true,
    "authorization_state": "WAITING",
    "pending_reason": "AWAITING_AUTHORIZATION",
    "authorized_at": null
  },
  "progress": {
    "total_files": 2,
    "processed_files": 0,
    "successful_files": 0,
    "failed_files": 0,
    "pending_files": 2,
    "percentage": 0.0,
    "started_at": null,
    "estimated_completion": null,
    "last_progress_at": null
  },
  "result_kind": "NONE",
  "terminal_info": null,
  "links": {
    "self": "/api/v1/processes/9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
    "status": "/api/v1/processes/9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e/status",
```

El challenge exige, como mínimo, identidad de proceso, estado, progreso, timestamps y resultados consultables por API; además muestra explícitamente una estructura con `process_id`, `status`, `progress`, `started_at`, `estimated_completion`, `results` y `files_processed`. La representación mantiene ese núcleo y lo formaliza mejor.

# 4. Commands públicos

## 4.1. Crear proceso

### Endpoint canónico

```text
POST /api/v1/processes
```

### Compatibilidad challenge

```text
POST /process/start
```

El challenge pide un endpoint de “start process”. Se reinterpreta como **create process in pending state**. 

### Request body

```json
{
  "objective": "analyze selected documents for lexical metrics and summary",
  "source_folder": "/data/input",
  "selection_mode": "EXPLICIT_SELECTION",
  "selected_files": [
    "doc-01.txt",
    "doc-02.txt"
  ],
  "batch_size": 1,
  "summary_policy": "EXTRACTIVE_DETERMINISTIC",
  "failure_policy": "TOLERATE_PARTIAL_FAILURES",
  "authorization_required": true
}
```

### Reglas semánticas

* `objective`: texto libre, útil para trazabilidad.
* `source_folder`: obligatorio.
* `selection_mode`: obligatorio.
* `selected_files`: obligatorio si `selection_mode = EXPLICIT_SELECTION`.
* `batch_size`: obligatorio, entero positivo.
* `summary_policy`: obligatorio.
* `failure_policy`: obligatorio.
* `authorization_required`: por defecto `true` en nuestra postura.

### Response

**201 Created**

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "PENDING",
  "message": "Process created and awaiting authorization.",
  "authorization": {
    "authorization_required": true,
    "authorization_state": "WAITING",
    "pending_reason": "AWAITING_AUTHORIZATION"
  },
  "links": {
    "status": "/api/v1/processes/9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e/status",
    "authorize": "/api/v1/processes/9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e/authorize",
    "results": "/api/v1/processes/9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e/results"
  }
}
```

### Errores

* `400 Bad Request`: JSON inválido o faltan campos obligatorios.
* `422 Unprocessable Entity`: request válida sintácticamente, pero semánticamente inviable.

## 4.2. Autorizar proceso

### Endpoint

```text
POST /api/v1/processes/{process_id}/authorize
```

### Request body

Vacío.

### Semántica

* válido solo en `PENDING`;
* concede autorización operacional;
* despacha el proceso al runtime;
* cambia el proceso a `RUNNING`.

### Response

**202 Accepted**

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "RUNNING",
  "message": "Process authorized and dispatched for execution."
}
```

### Errores

* `404 Not Found`: proceso inexistente.
* `409 Conflict`: el proceso no está en `PENDING`.

---

## 4.3. Pausar proceso

### Endpoint

```text
POST /api/v1/processes/{process_id}/pause
```

### Request body

Vacío.

### Semántica

* válido solo en `RUNNING`;
* registra intención de pausa;
* la transición estable a `PAUSED` puede no ser instantánea.

### Response

**202 Accepted**

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "RUNNING",
  "message": "Pause requested. Process will transition to PAUSED at a safe checkpoint."
}
```

### Errores

* `404 Not Found`
* `409 Conflict`

---

## 4.4. Reanudar proceso

### Endpoint


### Request body

Vacío.

### Semántica

* vuelve el proceso a `RUNNING`.

### Response

**202 Accepted**

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "RUNNING",
  "message": "Process resumed."
}
```

### Errores

* `404 Not Found`
* `409 Conflict`

## 4.5. Detener proceso

### Endpoint canónico

```text
POST /api/v1/processes/{process_id}/stop
```

### Compatibilidad challenge

```text
POST /process/stop/{process_id}
```

El challenge pide explícitamente un stop endpoint. 

### Request body

Vacío.

### Semántica

Válido en:

* `PENDING`
* `RUNNING`
* `PAUSED`

Comportamiento:

* desde `PENDING`: termina inmediatamente en `STOPPED`;
* desde `RUNNING`: registra intención de stop y converge a `STOPPED` en checkpoint seguro;
* desde `PAUSED`: termina inmediatamente en `STOPPED`.

### Response

**202 Accepted**

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "RUNNING",
  "message": "Stop requested. Process will transition to STOPPED at a safe checkpoint."
}
```

o, si estaba `PENDING` o `PAUSED`:

```json
{
  "process_id": "9b2d6613-2f7f-4f34-bc1d-66b7fd5d1b8e",
  "status": "STOPPED",
  "message": "Process stopped."
}
```

### Errores

* `404 Not Found`
* `409 Conflict`

# 9. Reglas normativas por endpoint

## 9.1. `POST /api/v1/processes`

* **MUST** crear el proceso en `PENDING`.
* **MUST NOT** comenzar análisis documental.
* **MUST** persistir plan y autorización.
* **MUST** devolver `201`.

## 9.2. `POST /api/v1/processes/{id}/authorize`

* **MUST** validar que el estado actual sea `PENDING`.
* **MUST** pasar el proceso a `RUNNING`.
* **MUST** registrar autorización.
* **SHOULD** inicializar materialización documental.

## 9.3. `POST /api/v1/processes/{id}/pause`

* **MUST** aceptar solo procesos `RUNNING`.
* **MUST** registrar intención de pausa.
* **SHOULD** completar la unidad mínima en curso antes de quedar en `PAUSED`.

## 9.4. `POST /api/v1/processes/{id}/resume`

* **MUST** aceptar solo procesos `PAUSED`.
* **MUST** volver a `RUNNING`.

## 9.5. `POST /api/v1/processes/{id}/stop`

* **MUST** aceptar `PENDING`, `RUNNING` o `PAUSED`.
* **MUST** terminar en `STOPPED`, nunca en `FAILED`.
* **MUST** preservar snapshot parcial si existía.

## 9.6. `GET /api/v1/processes/{id}/status`

* **MUST** devolver la vista operativa canónica.
* **MUST NOT** recalcular resultados.

## 9.7. `GET /api/v1/processes/{id}/results`

* **MUST** distinguir `NONE`, `PARTIAL` y `FINAL`.
* **MUST** derivar sus agregados de evidencia documental cerrada.
* **MUST NOT** presentar resultado final consolidado si el proceso no está `COMPLETED`.

# 11. Recomendación de cierre de especificación

Se congelan ya estas tres decisiones:

1. **Recurso principal**: `processes`
2. **JSON externo**: `snake_case`
3. **Contrato semántico**:

   * `start = create in pending`
   * `authorize = dispatch to running`
   * `pause/resume` operables
   * `results = none/partial/final`
