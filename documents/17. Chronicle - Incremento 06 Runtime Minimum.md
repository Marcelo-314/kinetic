# Chronicle - Incremento 06 Runtime Minimum

## Objetivo

Este incremento incorpora el runtime real mínimo de Chronicle con dispatcher, lease persistido, worker por `process_id` e integración efectiva con `ResolveCheckpoint`. Además corrige dos desajustes contractuales detectados en el incremento anterior para mantener la API pública alineada con la especificación aprobada.

## Alcance implementado

## 1. Correcciones contractuales

Se ajustó el contrato HTTP público en la capa web para alinearlo con la documentación congelada.

### Cambios aplicados

- `INVALID_TRANSITION` fue reemplazado por `INVALID_STATE_TRANSITION`
- la validación semántica dejó de usar nombres ad hoc y ahora expone códigos canónicos
- el mensaje de creación del proceso pasó a:
  - `Process created and awaiting authorization.`

### Resultado

La API web queda consistente con OpenAPI y con el catálogo de errores documentado.

## 2. Runtime real mínimo

Se implementó el runtime explícito en `adapters.out.runtime`, evitando `@Async` como modelo principal y sin usar Spring Batch.

### Componentes agregados

- `ProcessDispatcher`
- `ProcessWorker`
- `RuntimeScheduler`
- `DocumentAnalyzer`

### Características del runtime

- concurrencia entre procesos: sí
- concurrencia dentro del mismo proceso: no
- single-flight por `process_id`
- límite explícito de concurrencia
- integración real con `ResolveCheckpoint`
- checkpoint seguro al cierre de documento

El scheduler dispara ciclos de dispatch y el dispatcher selecciona procesos elegibles en `RUNNING`, adquiere lease y delega el trabajo al worker.

## 3. Lease / claim real

Se implementó `ProcessLeasePort` con persistencia real sobre H2/JPA.

### Capacidades

- `tryAcquire`
- `renew`
- `release`
- expiración de lease
- reclaim seguro tras expiración

### Resultado

El sistema evita doble ejecución concurrente del mismo proceso y conserva la posibilidad de recuperar procesos cuando un lease expire.

## 4. Materialización y ejecución documental mínima

El flujo de autorización ahora materializa los documentos del plan como `DocumentExecution` en estado `PENDING`.

Luego, el worker ejecuta este ciclo por proceso:

1. carga proceso, plan, progreso y flags
2. verifica `stop_requested` y `pause_requested`
3. resuelve checkpoint cuando corresponde
4. selecciona el siguiente documento pendiente
5. lo marca `PROCESSING`
6. procesa el archivo `.txt`
7. lo cierra como `PROCESSED` o `FAILED`
8. actualiza `ProgressSnapshot`
9. registra actividad operativa
10. reevalúa terminalidad

Se mantiene la regla de un único documento `PROCESSING` por proceso.

## 5. Procesamiento documental mínimo

Se implementó un pipeline deliberadamente simple y determinista para `.txt`.

### Análisis aplicado

- lectura del contenido del archivo
- conteo de caracteres
- conteo de líneas
- tokenización básica
- conteo de palabras
- top words mínimo
- resumen determinista simple a partir del contenido

### Manejo de fallos

Si un documento falla, el error queda registrado en `DocumentExecution` con:

- `documentStatus = FAILED`
- `errorCode`
- `errorMessage`

## 6. Persistencia adicional para runtime

Se agregó persistencia real para los elementos necesarios para que el runtime funcione end-to-end.

### Nuevos adapters / entidades

- persistencia JPA para `DocumentExecution`
- persistencia JPA para `ProcessLease`
- mapper explícito para `DocumentExecution`

### Queries mínimas soportadas

- procesos `RUNNING` elegibles
- siguiente documento pendiente por proceso
- documento `PROCESSING` por proceso
- conteo de pendientes por proceso

No se adelantó todavía una implementación completa de snapshots de `ProcessResult`.

## 7. Progress y activity operativos

Se actualiza `ProgressSnapshot` al cierre de cada documento, no antes.

También se registra actividad operativa básica mediante `ActivityLogEntry`, incluyendo:

- `PROCESS_AUTHORIZED`
- `PAUSE_REQUESTED`
- `PROCESS_PAUSED`
- `PROCESS_RESUMED`
- `STOP_REQUESTED`
- `PROCESS_STOPPED`
- `DOCUMENT_PROCESSED`
- `DOCUMENT_FAILED`
- `PROCESS_COMPLETED`
- `PROCESS_FAILED`

Se preserva el uso de `metadata` y `correlationId`.

## 8. Precedencias y checkpoint

El runtime integra de forma efectiva la semántica del dominio ya definida.

### Reglas respetadas

- `STOP > PAUSE`
- precedencia terminal:
  - `FAILED > STOPPED > COMPLETED > PAUSED`

El worker resuelve checkpoint:

- antes de iniciar un nuevo documento, si hay señales de control pendientes
- al cierre del documento
- cuando ya no quedan documentos pendientes

## 9. Ajuste de locking en persistencia de Process

Se refinó `ProcessRepositoryAdapter` para distinguir entre:

- actualizaciones técnicas válidas del mismo `version`
- escrituras stale que deben fallar por optimistic locking

Esto preserva dos necesidades simultáneas:

- permitir updates técnicos del runtime sin forzar transiciones artificiales
- mantener protección real frente a conflictos concurrentes

La semántica observable de `version` no cambió.

## 10. Qué no se implementó todavía

Se respetaron estas restricciones del incremento:

- no `GET /api/v1/processes/{id}/results` completo
- no `GET /api/v1/processes/{id}/activity` completo
- no agregación final compleja de resultados
- no Spring Batch
- no Spring State Machine
- no lógica de runtime en controllers
- no JPA en dominio

## 11. Tests agregados y actualizados

Se agregaron o ajustaron pruebas para cubrir el nuevo comportamiento.

### Runtime / integración

- dispatcher detecta procesos `RUNNING` elegibles
- lease evita doble ejecución del mismo proceso
- reclaim tras expiración de lease
- worker procesa un documento y actualiza progreso
- `stop_requested` prevalece sobre `pause_requested`
- integración real con `ResolveCheckpoint`
- documento fallido queda `FAILED`
- el proceso pasa a `PAUSED`, `STOPPED`, `COMPLETED` o `FAILED` según corresponda

### Web / contrato

- código público `INVALID_STATE_TRANSITION`
- mensaje de creación alineado con `PENDING`
- validación semántica con códigos canónicos

### Persistencia

- optimistic locking real de `Process`
- soporte de persistencia para `DocumentExecution`
- compatibilidad del runtime con adapters JPA/H2

## Resultado

Chronicle queda ahora con un runtime mínimo real y defendible, apoyado en persistencia JPA/H2, lease con expiración y ejecución single-flight por proceso.

El sistema ya no depende solo de la semántica de lifecycle y de la API web: puede autorizar procesos, materializar trabajo documental, ejecutar documentos `.txt`, actualizar progreso por checkpoint y cerrar procesos de forma consistente con las precedencias aprobadas.

El cambio se mantuvo incremental y revisable, sin adelantar todavía `results` completos, activity pública completa ni infraestructura más compleja de runtime.
