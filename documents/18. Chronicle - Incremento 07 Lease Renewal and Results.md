# Chronicle - Incremento 07 Lease Renewal and Results

## Objetivo

Este incremento robustece el runtime con renovación real de lease durante el procesamiento documental, cierra la semántica de `STOPPED` frente a `result_kind`, alinea por completo la narrativa de "awaiting authorization" y expone `GET /api/v1/processes/{process_id}/results` con una proyección mínima pero real basada en evidencia documental cerrada.

## Alcance implementado

## 1. Lease renewal real

Se extendió el runtime para que el worker pueda renovar activamente el lease mientras procesa un documento.

### Cambios aplicados

- `ProcessDispatcher` ahora entrega al worker el `ownerId` y la duración del lease
- `ProcessWorker` inicia una sesión de renovación periódica mientras dura el análisis documental
- se mantiene el comportamiento ya existente de:
  - `tryAcquire`
  - `release`
  - expiración
  - reclaim seguro

### Resultado

El lease ya no depende de que `lease-duration` sea "suficientemente largo": se renueva de forma real durante documentos prolongados, evitando reacquire indebido del mismo `process_id`.

## 2. Cierre semántico de `STOPPED` vs `result_kind`

Se aplicó explícitamente esta decisión:

- `STOPPED -> NONE` cuando no existe evidencia documental cerrada
- `STOPPED -> PARTIAL` cuando sí existe evidencia documental cerrada

La misma lógica también quedó alineada para:

- `FAILED -> NONE` si el fallo ocurre antes de generar evidencia cerrada
- `FAILED -> PARTIAL` si sí existe evidencia cerrada
- `COMPLETED -> FINAL`

### Resultado

El sistema deja de forzar `PARTIAL` o `FINAL` artificialmente y refleja de forma honesta la evidencia realmente disponible.

## 3. Cierre completo de "awaiting authorization"

Se alineó la narrativa interna con la pública.

### Cambios aplicados

- el mensaje HTTP de creación sigue siendo:
  - `Process created and awaiting authorization.`
- `PROCESS_CREATED` en `ActivityLogEntry` ahora usa esa misma semántica
- la metadata asociada incorpora contexto de autorización:
  - `status`
  - `authorization_state`
  - `pending_reason`

### Resultado

La trazabilidad interna ya no contradice la intención semántica aprobada para `PENDING`.

## 4. ProcessResult mínimo real

Se implementó una proyección mínima real de resultados apoyada en evidencia documental cerrada.

### Componentes agregados

- `ProcessResultProjectionService`
- persistencia JPA para `ProcessResult`
- mapper explícito `ProcessResultPersistenceMapper`
- adapter `ProcessResultRepositoryAdapter`

### Regla de agregación

La proyección se construye desde `DocumentExecution` cerrados:

- incluye documentos `PROCESSED`
- excluye `PROCESSING`
- no suma documentos `FAILED` a agregados de éxito
- sí refleja documentos fallidos en `excludedDocuments`

### Campos calculados

- `resultKind`
- `computedAt`
- `coverage`
- `totalWords`
- `totalLines`
- `totalCharacters`
- `mostFrequentWords`
- `includedDocuments`
- `excludedDocuments`
- `documentSummaries`
- `globalSummary`
- `isFinal`

### Regla para `globalSummary`

- canónico solo cuando `resultKind = FINAL`
- fuera de `FINAL`, se expone `null`

## 5. Persistencia de snapshots derivados

`ProcessResult` se mantiene como snapshot derivado, no como fuente primaria de verdad.

### Comportamiento actual

- el worker genera snapshot al cierre de documento y en checkpoint relevante
- la proyección se persiste cuando existe evidencia real o cuando el proceso llega a `COMPLETED`
- la evidencia fuente sigue estando en:
  - `DocumentExecution`
  - `Process`
  - `TerminalInfo`

## 6. Endpoint real de results

Se implementó `GET /api/v1/processes/{process_id}/results` alineado con OpenAPI.

### Características

- controller delgado
- DTOs web externos separados
- uso de capa application
- payload externo en `snake_case`

### Query params soportados

- `include_documents`
- `include_global_summary`
- `top_words_limit`

### Semántica expuesta

- `PENDING -> NONE`
- `RUNNING -> NONE` en ventana inicial sin evidencia
- `RUNNING -> PARTIAL` si ya existe evidencia
- `PAUSED -> NONE` si no hay evidencia, `PARTIAL` si la hay
- `STOPPED -> NONE` si no hay evidencia, `PARTIAL` si la hay
- `FAILED -> NONE` si no hay evidencia, `PARTIAL` si la hay
- `COMPLETED -> FINAL`

### Regla fuerte respetada

No se fabrica `FINAL` si el proceso no está `COMPLETED`.

## 7. Ajustes de modelos y DTOs

Se agregaron los DTOs web mínimos para `results`:

- `ProcessResultsResponseDto`
- `CoverageViewDto`
- `TotalsViewDto`
- `DocumentResultDto`
- `ExcludedDocumentDto`
- `WordFrequencyDto`

También se agregó la query/view de application para desacoplar la capa web:

- `GetProcessResultsQuery`
- `ProcessResultsView`
- `GetProcessResultsUseCase`

## 8. Integración con runtime

La proyección de resultados quedó integrada con el runtime ya existente:

- al cierre de documento
- al checkpoint
- al cierre terminal

Esto mantiene consistencia entre:

- lifecycle visible
- progreso
- evidencia documental
- snapshot analítico vigente

## 9. Qué no se implementó todavía

Se mantuvieron las restricciones del incremento:

- no `GET /api/v1/processes/{process_id}/activity` completo
- no agregación compleja o avanzada de resultados
- no runtime en controllers
- no Spring Batch
- no Spring State Machine
- no JPA en dominio
- no `ProcessResult` como fuente primaria de verdad

## 10. Tests agregados y actualizados

Se incorporó cobertura para los nuevos requisitos.

### Lease renewal

- el lease se renueva durante procesamiento largo
- no hay reacquire indebido mientras el worker sigue vivo
- reclaim sigue funcionando cuando el lease realmente expira

### Results semantics

- `PENDING -> NONE`
- `STOPPED -> NONE` sin evidencia
- `STOPPED -> PARTIAL` con evidencia
- `FAILED -> NONE` sin evidencia
- `FAILED -> PARTIAL` con evidencia
- `COMPLETED -> FINAL`

### Endpoint `/results`

- `200` con payload correcto
- `include_documents=false`
- `include_global_summary=false`
- `top_words_limit` aplicado
- `404` para proceso inexistente

### Awaiting authorization

- actividad interna de create alineada con `"Process created and awaiting authorization."`
- consistencia entre mensaje público y trazabilidad interna

Verificación ejecutada:

```bash
mvn test
```

Resultado:

- `61` tests pasando

## Resultado

Chronicle queda ahora con un runtime más robusto frente a documentos largos gracias a la renovación real del lease, y con una primera proyección de resultados honestamente alineada con la evidencia cerrada disponible.

El endpoint `/results` ya es funcional y consistente con la OpenAPI aprobada, sin adelantar agregación analítica compleja ni activity pública completa. También queda cerrada de forma explícita la semántica de `STOPPED` frente a `result_kind` y la narrativa completa de "awaiting authorization" en el plano público e interno.
