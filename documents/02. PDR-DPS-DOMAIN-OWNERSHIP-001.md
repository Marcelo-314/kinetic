
# PDR-DPS-DOMAIN-OWNERSHIP-001

**Título:** Domain Model and Ownership
**Versión:** v0.1-draft
**Estado:** Draft
**Predecesor normativo:** RFC-DPS-LIFECYCLE-API-001
**Ámbito:** Document Processing Service

## 1. Propósito

Este PDR traduce el RFC de lifecycle y semántica de API a un **modelo de dominio explícito**, definiendo:

* qué objetos existen en el sistema,
* qué significado tiene cada objeto,
* qué campos son canónicos,
* qué componente es dueño de cada mutación,
* qué invariantes deben preservarse.

El challenge exige un servicio con procesos observables por API, estados persistidos, resultados recuperables, logs de actividad y procesamiento asíncrono por lotes de documentos `.txt`. Por eso, el dominio no puede reducirse a “un proceso con algunos campos”, sino que requiere separar lifecycle, evidencia documental, agregación analítica y trazabilidad. 

## 2. Relación con el RFC previo

Este PDR **no redefine**:

* estados del proceso,
* transiciones válidas,
* semántica de endpoints,
* semántica `NONE / PARTIAL / FINAL`.

Eso ya quedó congelado en el RFC.

Este PDR **sí define**:

* el agregado raíz del dominio,
* los objetos satélite,
* las unidades de evidencia,
* las proyecciones analíticas,
* la ownership model de lectura y escritura.

## 3. Principios de diseño

### 3.1. Separación entre control y analítica

El plano de control gobierna el lifecycle del proceso.
El plano analítico produce evidencia y proyecciones.

### 3.2. Evidencia antes que agregado

El sistema DEBE tratar al documento procesado como unidad mínima de evidencia.
Los agregados del proceso DEBEN derivarse de esa evidencia, no reemplazarla.

### 3.3. Un solo dueño por mutación relevante

Cada campo canónico del dominio DEBE tener un único dueño semántico de escritura.

### 3.4. Estados terminales absorbentes

La terminalidad del proceso NO DEBE ser reabierta ni reinterpretada.

### 3.5. El log no es la fuente de verdad

Los logs explican hechos; no reemplazan al estado canónico del proceso.

## 4. Vista general del dominio

El dominio queda organizado en cuatro capas conceptuales:

### 4.1. Agregado raíz

* `Process`

### 4.2. Objetos satélite del lifecycle

* `ProcessPlan`
* `AuthorizationInfo`
* `ProgressSnapshot`
* `ExecutionControlFlags`
* `TerminalInfo`

### 4.3. Evidencia operativa y analítica

* `DocumentExecution`
* `BatchExecution` (recomendado)
* `ActivityLogEntry`

### 4.4. Proyección agregada

* `ProcessResult`

## 5. Agregado raíz: `Process`

## 5.1. Rol

`Process` es la entidad top-level expuesta por la API.
Representa una corrida identificable, con lifecycle observable y resultados asociados.

## 5.2. Campos canónicos

* `process_id`
* `status`
* `version`
* `created_at`
* `updated_at`
* `objective`
* `plan_ref`
* `authorization_ref`
* `progress_ref`
* `terminal_info_ref`
* `current_result_ref`
* `last_activity_at`

## 5.3. Semántica

### `process_id`

Identidad estable del proceso.
DEBE ser única y pública a nivel API.

### `status`

Estado canónico del lifecycle.
SOLO puede tomar valores del conjunto definido por el RFC:
`PENDING | RUNNING | PAUSED | COMPLETED | FAILED | STOPPED`.

### `version`

Revisión monotónica del agregado.
Se introduce para control de concurrencia y coherencia de actualizaciones.

### `created_at` / `updated_at`

Timestamps de creación y última mutación relevante del agregado.

### `objective`

Descripción textual del propósito del proceso.
No gobierna el lifecycle, pero mejora trazabilidad.

### `*_ref`

Referencias canónicas a satélites o proyecciones asociadas.

## 5.4. Invariantes de `Process`

* `process_id` es inmutable.
* `status` solo cambia por transición válida.
* `version` nunca decrece.
* si `status` es terminal, `terminal_info_ref` DEBE existir.
* si `status = PENDING`, no DEBE existir evidencia documental cerrada.
* `updated_at >= created_at`.

## 5.5. Qué NO debe vivir en `Process`

No debe contener embebidos:

* métricas por documento,
* frecuencias completas,
* summaries documentales,
* logs append-only.

`Process` es el centro del lifecycle, no un contenedor universal.

# 6. `ProcessPlan`

## 6.1. Rol

Define el alcance congelado del trabajo.

## 6.2. Campos canónicos

* `plan_id`
* `source_folder`
* `selection_mode`
* `selected_files`
* `total_planned_files`
* `batch_size`
* `summary_policy`
* `failure_policy`
* `created_at`

## 6.3. Semántica

### `source_folder`

Carpeta fuente desde la cual se seleccionan documentos.
El challenge exige carga desde una carpeta específica. 

### `selection_mode`

Modo de selección del corpus:

* `ALL_FROM_FOLDER`
* `EXPLICIT_SELECTION`

### `selected_files`

Conjunto exacto de archivos objetivo del proceso.

### `total_planned_files`

Cardinalidad canónica esperada del corpus.

### `batch_size`

Tamaño lógico de lote.
Se justifica porque el challenge exige batch processing. 

### `summary_policy`

Política formal del summary.
Inicialmente: `EXTRACTIVE_DETERMINISTIC`.

### `failure_policy`

Política de fallo del proceso:

* `FAIL_FAST`
* `TOLERATE_PARTIAL_FAILURES`

## 6.4. Invariantes de `ProcessPlan`

* es inmutable tras creación;
* `batch_size > 0`;
* `total_planned_files = cardinalidad real del conjunto seleccionado`;
* si `selection_mode = EXPLICIT_SELECTION`, `selected_files` no puede ser vacío.

# 7. `AuthorizationInfo`

## 7.1. Rol

Expresa la condición operacional que da sentido real a `PENDING`.

## 7.2. Campos canónicos

* `authorization_info_id`
* `authorization_required`
* `authorization_state`
* `pending_reason`
* `authorized_at`
* `authorization_note`
* `last_authorization_update_at`

## 7.3. Semántica

### `authorization_required`

Indica si el proceso requiere autorización previa para ser despachado.

### `authorization_state`

Valores canónicos:

* `WAITING`
* `AUTHORIZED`
* `REJECTED`
* `NOT_REQUIRED`

### `pending_reason`

Razón de permanencia en `PENDING`.
Típicamente: `AWAITING_AUTHORIZATION`.

### `authorized_at`

Instante de autorización efectiva.

## 7.4. Invariantes

* si `authorization_state = AUTHORIZED`, `authorized_at` DEBE existir;
* si el proceso está `PENDING`, el bloque de autorización DEBE explicar por qué sigue pendiente;
* este objeto NO modela aún identidad/autenticación de usuario.

---

# 8. `ProgressSnapshot`

## 8.1. Rol

Representa la vista cuantitativa observable del avance del proceso.

El challenge muestra explícitamente progreso con `total_files`, `processed_files`, `percentage`, `started_at` y `estimated_completion`. Este PDR extiende ese bloque con campos necesarios para consistencia operativa. 

## 8.2. Campos canónicos

* `progress_snapshot_id`
* `process_id`
* `total_files`
* `processed_files`
* `successful_files`
* `failed_files`
* `pending_files`
* `percentage`
* `current_batch_index`
* `current_batch_size`
* `started_at`
* `estimated_completion`
* `last_progress_at`

## 8.3. Semántica

### `processed_files`

Cantidad de documentos cuyo tratamiento ya concluyó, exitosamente o con fallo documental.

### `successful_files`

Cantidad de documentos cerrados como `PROCESSED`.

### `failed_files`

Cantidad de documentos cerrados como `FAILED`.

### `pending_files`

Cantidad todavía no cerrada.

### `percentage`

Porcentaje observable de avance del proceso.

## 8.4. Invariantes

* `processed_files <= total_files`
* `successful_files + failed_files <= processed_files`
* `pending_files = total_files - processed_files`
* `percentage` debe ser consistente con el cociente observable
* en `PENDING`, `processed_files = 0`
* `started_at` no debe existir antes de ejecución efectiva

## 8.5. Naturaleza del objeto

Este PDR recomienda tratar `ProgressSnapshot` como **snapshot reemplazable**, no como log append-only.

---

# 9. `ExecutionControlFlags`

## 9.1. Rol

Representa intenciones de control hacia el runtime.
No es un estado de dominio visible.

## 9.2. Campos canónicos

* `process_id`
* `pause_requested`
* `stop_requested`
* `last_control_command_at`
* `last_control_command_type`

## 9.3. Semántica

### `pause_requested`

Existe una solicitud vigente de pausa todavía no convergida a `PAUSED`.

### `stop_requested`

Existe una solicitud vigente de stop todavía no convergida a `STOPPED`.

## 9.4. Invariantes

* estos flags NO reemplazan a `status`;
* `pause_requested = true` no implica `PAUSED`;
* `stop_requested = true` no implica terminalidad instantánea;
* `resume` debe limpiar la intención de pausa.

## 9.5. Nota de diseño

Este objeto es recomendado para mantener una frontera limpia entre:

* aceptación del command externo,
* convergencia estable del lifecycle.

---

# 10. `TerminalInfo`

## 10.1. Rol

Captura la causalidad terminal del proceso.

## 10.2. Campos canónicos

* `terminal_info_id`
* `process_id`
* `terminal_state`
* `terminal_at`
* `terminal_reason_code`
* `terminal_reason_message`
* `final_coverage`

## 10.3. Semántica

### `terminal_state`

Solo puede ser:

* `COMPLETED`
* `FAILED`
* `STOPPED`

### `terminal_reason_code`

Código canónico de causalidad terminal, por ejemplo:

* `NORMAL_COMPLETION`
* `MANUAL_STOP`
* `IO_ERROR`
* `DOCUMENT_FAILURE_POLICY_TRIGGERED`

### `final_coverage`

Cobertura final alcanzada por el proceso al momento de terminar.

## 10.4. Invariantes

* existe solo para procesos terminales;
* una vez fijado, no cambia;
* `terminal_state` debe coincidir con `Process.status`.

# 11. `DocumentExecution`

## 11.1. Rol

Es la **unidad mínima de evidencia** del dominio.

## 11.2. Campos canónicos

* `document_execution_id`
* `process_id`
* `document_path`
* `document_name`
* `document_status`
* `batch_index`
* `started_at`
* `finished_at`
* `word_count`
* `line_count`
* `character_count`
* `most_frequent_words`
* `summary`
* `summary_method`
* `error_code`
* `error_message`

## 11.3. Semántica

### `document_status`

Estados canónicos:

* `PENDING`
* `PROCESSING`
* `PROCESSED`
* `FAILED`
* `SKIPPED`

### Métricas analíticas

* `word_count`
* `line_count`
* `character_count`
* `most_frequent_words`
* `summary`

Estas corresponden al tipo de resultados exigidos por el challenge: estadísticas básicas, top frequent words y summary. 

## 11.4. Invariantes

* si `document_status = PROCESSED`, deben existir métricas y summary;
* si `document_status = FAILED`, deben existir `error_code` y/o `error_message`;
* `finished_at >= started_at` cuando ambos existen;
* dentro del mismo proceso, una ejecución documental NO debe pasar de `FAILED` a `PROCESSED`.

## 11.5. Regla fuerte

`DocumentExecution` es evidencia; no es una mera cache del agregado.

---

# 12. `BatchExecution` (recomendado)

## 12.1. Rol

Representa la unidad operacional de lote.

## 12.2. Campos canónicos

* `batch_execution_id`
* `process_id`
* `batch_index`
* `document_execution_ids`
* `batch_status`
* `started_at`
* `finished_at`
* `documents_succeeded`
* `documents_failed`

## 12.3. Semántica

El batch permite:

* checkpointing ordenado,
* diagnóstico de ejecución,
* pausa/stop en puntos seguros,
* visibilidad del avance por lote.

## 12.4. Invariantes

* `batch_index` es único dentro del proceso;
* los documentos asignados al batch no cambian;
* `documents_succeeded + documents_failed <= cantidad de documentos del lote`.

## 12.5. Nota

`BatchExecution` no es estrictamente obligatorio para exponer API, pero este PDR lo recomienda como objeto de diseño interno de primer orden.

---

# 13. `ProcessResult`

## 13.1. Rol

Es la proyección analítica agregada del proceso.

## 13.2. Campos canónicos

* `process_result_id`
* `process_id`
* `result_kind`
* `computed_at`
* `included_documents`
* `excluded_documents`
* `total_words`
* `total_lines`
* `total_characters`
* `most_frequent_words`
* `document_summaries`
* `global_summary`
* `coverage`
* `is_final`

## 13.3. Semántica

### `result_kind`

Valores canónicos:

* `NONE`
* `PARTIAL`
* `FINAL`

### `included_documents`

Documentos `PROCESSED` incorporados al agregado.

### `excluded_documents`

Documentos no incorporados al agregado y su causalidad.

### `coverage`

Cobertura efectiva del agregado sobre el plan.

## 13.4. Invariantes

* `FINAL` solo si el proceso está `COMPLETED`;
* `included_documents` solo puede contener evidencia documental cerrada con éxito;
* `global_summary` solo es canónico si `result_kind = FINAL`.

## 13.5. Regla fuerte

`ProcessResult` es un **snapshot inmutable**.
Cuando cambia la evidencia disponible, se genera un nuevo snapshot.

# 14. `ActivityLogEntry`

## 14.1. Rol

Representa hechos operativos append-only del proceso.

El challenge exige persistir logs de actividad. Este objeto es la formalización de ese requisito. 

## 14.2. Campos canónicos

* `activity_id`
* `process_id`
* `timestamp`
* `event_type`
* `event_stage`
* `message`
* `metadata`
* `correlation_id`

## 14.3. Semántica

### `event_type`

Ejemplos canónicos:

* `PROCESS_CREATED`
* `PROCESS_AUTHORIZED`
* `PAUSE_REQUESTED`
* `PROCESS_PAUSED`
* `PROCESS_RESUMED`
* `DOCUMENT_PROCESSED`
* `DOCUMENT_FAILED`
* `PROCESS_STOPPED`
* `PROCESS_FAILED`
* `PROCESS_COMPLETED`
* `PARTIAL_RESULT_SNAPSHOTTED`
* `FINAL_RESULT_SNAPSHOTTED`

### `event_stage`

Capa de origen del hecho:

* `API`
* `ORCHESTRATION`
* `RUNTIME`
* `ANALYSIS`
* `RESULTS`

## 14.4. Invariantes

* append-only;
* nunca corrige ni reemplaza `Process.status`;
* sirve para explicar y auditar, no para gobernar terminalidad.

# 15. Ownership model

Ahora cierro la cuestión central: quién crea, lee y puede mutar cada objeto.

## 15.1. Componentes lógicos

Este PDR fija los siguientes componentes conceptuales:

* `API Layer`
* `Process Orchestrator`
* `Authorization Service`
* `Runtime Scheduler`
* `Batch Planner`
* `Document Analyzer`
* `Result Aggregator`
* `Activity Logger`
* `Persistence Layer`

## 15.2. Ownership por objeto

| Objeto                  | Crea                              | Lee                            | Muta                                     | Dueño semántico       |
| ----------------------- | --------------------------------- | ------------------------------ | ---------------------------------------- | --------------------- |
| `Process`               | Process Orchestrator              | todos los lectores de control  | Process Orchestrator                     | Process Orchestrator  |
| `ProcessPlan`           | Process Orchestrator              | Runtime, Batch Planner, API    | nadie tras creación                      | Process Orchestrator  |
| `AuthorizationInfo`     | Process Orchestrator              | API, Orchestrator, Runtime     | Authorization Service                    | Authorization Service |
| `ProgressSnapshot`      | Runtime Scheduler                 | API, Orchestrator, Results     | Runtime Scheduler                        | Runtime Scheduler     |
| `ExecutionControlFlags` | Process Orchestrator              | Runtime Scheduler              | Process Orchestrator / Runtime Scheduler | Runtime Scheduler     |
| `TerminalInfo`          | Process Orchestrator              | API, Results                   | Process Orchestrator                     | Process Orchestrator  |
| `DocumentExecution`     | Batch Planner / Runtime Scheduler | Analyzer, Results, API detalle | Document Analyzer / Runtime Scheduler    | Document Analyzer     |
| `BatchExecution`        | Batch Planner                     | Runtime, API opcional          | Runtime Scheduler                        | Runtime Scheduler     |
| `ProcessResult`         | Result Aggregator                 | API, Orchestrator              | nadie tras creación                      | Result Aggregator     |
| `ActivityLogEntry`      | Activity Logger o emisor          | auditoría, API opcional        | nadie                                    | Activity Logger       |

## 15.3. Reglas fuertes de ownership

### 15.3.1.

Solo el **Process Orchestrator** puede mutar `Process.status`.

### 15.3.2.

Solo el **Authorization Service** puede mutar `authorization_state`.

### 15.3.3.

Solo el **Runtime Scheduler** puede mutar el snapshot de progreso.

### 15.3.4.

Solo el **Document Analyzer** puede cerrar analíticamente un documento como `PROCESSED` o `FAILED`.

### 15.3.5.

Solo el **Result Aggregator** puede emitir `ProcessResult`.

### 15.3.6.

Los logs pueden ser emitidos desde distintos componentes, pero su materialización persistente DEBE ser responsabilidad del **Activity Logger**.

# 16. Ownership por campo crítico

## `Process.status`

* escribe: Process Orchestrator
* leen: API, Runtime, Results, Authorization
* nadie más muta

## `AuthorizationInfo.authorization_state`

* escribe: Authorization Service
* leen: API, Orchestrator, Runtime

## `ProgressSnapshot.processed_files`

* escribe: Runtime Scheduler
* leen: API, Orchestrator, Result Aggregator

## `DocumentExecution.word_count`, `summary`, `most_frequent_words`

* escribe: Document Analyzer
* leen: Result Aggregator, API detalle

## `ProcessResult.result_kind`

* escribe: Result Aggregator
* leen: API, Orchestrator

## `TerminalInfo.terminal_state`

* escribe: Process Orchestrator
* leen: API, Result Aggregator

---

# 17. Reglas de acoplamiento

## 17.1.

El API Layer NO DEBE mutar repositorios de dominio directamente.

## 17.2.

El Document Analyzer NO DEBE cambiar `Process.status`.

## 17.3.

El Result Aggregator NO DEBE inventar evidencia; solo puede consolidar `DocumentExecution` cerrados.

## 17.4.

El Runtime Scheduler NO DEBE fijar terminalidad de negocio directamente; puede detectar condiciones y notificar al Orchestrator.

## 17.5.

Los logs NO DEBEN usarse como fuente de verdad del lifecycle.

# 18. Flujo mínimo de ownership

## 18.1. Creación

1. API recibe request.
2. Process Orchestrator crea `Process`, `ProcessPlan`, `AuthorizationInfo`.
3. Activity Logger registra `PROCESS_CREATED`.

## 18.2. Autorización

1. API invoca autorización.
2. Authorization Service actualiza `AuthorizationInfo`.
3. Process Orchestrator fija `RUNNING`.
4. Runtime Scheduler materializa progreso inicial.
5. Activity Logger registra.

## 18.3. Ejecución

1. Batch Planner define lotes.
2. Runtime Scheduler activa ejecuciones documentales.
3. Document Analyzer produce evidencia.
4. Runtime Scheduler actualiza progreso.
5. Result Aggregator emite snapshots parciales.
6. Activity Logger registra hitos.

## 18.4. Pausa / resume / stop

1. API emite command.
2. Process Orchestrator registra intención de control.
3. Runtime Scheduler aplica convergencia.
4. Orchestrator fija el estado estable resultante.
5. Activity Logger registra.

## 18.5. Terminación

1. Runtime detecta cierre o error.
2. Process Orchestrator fija `COMPLETED`, `FAILED` o `STOPPED`.
3. Process Orchestrator crea `TerminalInfo`.
4. Result Aggregator emite snapshot final o parcial terminal.
5. Activity Logger registra.

---

# 19. Reglas de persistencia conceptual

Este PDR no baja aún a tecnología, pero fija la naturaleza lógica de persistencia.

## 19.1. Persistencia mutable

* `Process`
* `AuthorizationInfo`
* `ProgressSnapshot`
* `ExecutionControlFlags`

## 19.2. Persistencia inmutable tras cierre

* `ProcessPlan`
* `TerminalInfo`
* `DocumentExecution` cerrado
* `BatchExecution` cerrado
* `ProcessResult`
* `ActivityLogEntry`

## 19.3. Implicancia

El dominio mezcla:

* objetos de estado actual,
* objetos de evidencia,
* objetos de proyección.

Esa mezcla es deliberada y necesaria.

# 20. Open questions para ADR/SDD

Este PDR deja abiertas, para siguientes artefactos, estas decisiones:

* checkpoint exacto de pausa/stop: fin de documento vs fin de batch;
* necesidad definitiva de `BatchExecution` como entidad persistida;
* granularidad de snapshots de `ProcessResult`;
* repositorios concretos y esquema físico;
* tipo de control de concurrencia sobre `Process.version`.

# 21. Dictamen

Este PDR fija un modelo de dominio suficientemente estable para pasar a la siguiente capa: **comportamiento operativo del sistema**.
