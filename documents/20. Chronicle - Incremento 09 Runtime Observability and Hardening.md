# Chronicle - Incremento 09 Runtime Observability and Hardening

## Objetivo

Este incremento mejora la observabilidad operativa de Chronicle y endurece el runtime ante estados anomalos y recuperacion parcial, manteniendo la arquitectura hexagonal y evitando introducir complejidad lateral innecesaria.

## Alcance implementado

## 1. Observabilidad operativa del runtime

Se agrego observabilidad real y acotada para diagnosticar el comportamiento del dispatcher, los leases, los workers, los checkpoints y el procesamiento documental.

### Logging estructurado

Se incorporo logging estructurado y consistente para eventos relevantes del runtime.

### Campos incluidos cuando aplican

- `process_id`
- `document_execution_id`
- `event_type`
- `correlation_id`
- `lease_owner_id`
- `process_status`
- `document_status`

### Eventos loggeados

- inicio y fin de scan del dispatcher
- `LEASE_ACQUIRED`
- `LEASE_RENEWED`
- `LEASE_RENEWAL_FAILED`
- inicio de worker
- aborto de worker por perdida de lease
- `CHECKPOINT_RESOLVED`
- inicio de procesamiento documental
- documento procesado
- documento fallido
- proceso pausado
- proceso detenido
- proceso completado
- proceso fallido

## 2. Metricas operativas minimas

Se agrego instrumentacion con Micrometer y Actuator, sin sobredisenar una plataforma de observabilidad mas amplia.

### Contadores incorporados

- `processes_dispatched_total`
- `lease_acquired_total`
- `lease_renewal_success_total`
- `lease_renewal_failure_total`
- `worker_abort_due_to_lease_loss_total`
- `documents_processed_total`
- `documents_failed_total`
- `checkpoint_resolutions_total`
- `process_completed_total`
- `process_failed_total`
- `process_paused_total`
- `process_stopped_total`

### Timers incorporados

- `document_processing_duration`
- `process_dispatch_duration`

## 3. Health y visibilidad minima del runtime

Se agrego soporte minimo de visibilidad operativa usando Actuator y un health indicator propio del runtime.

### Componentes incorporados

- `spring-boot-starter-actuator`
- exposicion de `health`, `info` y `metrics`
- `ChronicleRuntimeHealthIndicator`

### Comportamiento

El health indicator revisa documentos que hayan quedado en `PROCESSING` sin lease activo y expone esa condicion como senal de degradacion operativa.

## 4. Runtime hardening ante estados anomalos

Se endurecio el runtime para evitar huerfanos operativos silenciosos y mejorar la recuperacion de estados residuales.

### Estrategia aplicada

Se incorporo un `RuntimeRecoveryService` ligero que se ejecuta antes del scan del dispatcher.

### Casos tratados

- documento en `PROCESSING` sin lease activo
- lease expirado con estado operativo parcial

### Comportamiento

Si se detecta un documento en `PROCESSING` cuyo proceso ya no tiene lease activo:

- el documento vuelve a `PENDING`
- no se fabrica evidencia documental
- no se consolida progreso invalido
- se registra `RUNTIME_RECOVERY_APPLIED`

## 5. Endurecimiento fino de la perdida de lease

La semantica introducida en el incremento anterior se mantuvo y se reforzaron sus bordes.

### Garantias actuales

- si falla la renovacion del lease, el worker no sigue procesando como si siguiera siendo duenio valido
- el documento en curso no se consolida como evidencia cerrada
- el progreso no se incrementa artificialmente
- el cleanup operativo queda consistente
- se registra actividad util del incidente

### Resultado

El sistema preserva exclusividad por `process_id`, checkpoint seguro y consistencia entre progreso, evidencia y terminalidad.

## 6. Activity operativa enriquecida

Se consolido activity como plano persistido de hechos relevantes del runtime.

### Eventos operativos agregados o reforzados

- `LEASE_ACQUIRED`
- `LEASE_RENEWED`
- `LEASE_RENEWAL_FAILED`
- `WORKER_STARTED`
- `WORKER_ABORTED`
- `DOCUMENT_PROCESSING_STARTED`
- `CHECKPOINT_RESOLVED`
- `RUNTIME_RECOVERY_APPLIED`

## 7. Consistencia entre logs, activity y metricas

Se separaron responsabilidades para evitar duplicacion ciega:

- `activity` persiste hechos operativos relevantes
- los logs estructurados sirven para diagnostico tecnico
- las metricas exponen senales cuantitativas del runtime

La implementacion busca alineacion razonable entre los tres planos sin convertirlos en duplicados exactos.

## 8. Adaptaciones de puertos y persistencia

Se extendieron contratos y adapters solo en lo necesario para sostener recovery y observabilidad.

### Ajustes principales

- `ProcessLeasePort` ahora soporta verificacion de lease activo y consulta de `owner_id`
- `DocumentExecutionRepository` ahora permite buscar documentos en `PROCESSING`
- adapters JPA extendidos para leases y documentos en procesamiento

No se altero el dominio con anotaciones de framework ni se rehizo el runtime existente.

## 9. Que no se implemento todavia

Se mantuvieron las restricciones del incremento:

- no se cambio el contrato funcional publico principal
- no se introdujeron colas externas
- no Spring Batch
- no Spring State Machine
- no JPA en dominio
- no se rehizo completamente el runtime
- no se agrego una plataforma de observabilidad desproporcionada

## 10. Tests agregados y actualizados

Se agrego cobertura para hardening operativo, recovery y observabilidad minima.

### Runtime hardening

- documento huerfano en `PROCESSING` se reconcilia antes de tomar trabajo nuevo
- lease perdido no deja evidencia ni progreso invalido
- no se procesa dos veces el mismo `process_id`
- cleanup consistente tras aborto del worker

### Observabilidad

- eventos operativos relevantes generan `ActivityLogEntry` cuando corresponde
- metricas criticas se incrementan en puntos clave
- health de Actuator queda disponible y funcional

### Persistencia y consultas

- deteccion de documentos `PROCESSING`
- deteccion de lease activo por proceso
- soporte de recovery basado en estado persistido

## Resultado

Chronicle queda ahora mas observable y mas robusto ante incidentes operativos del runtime. El sistema ofrece trazabilidad util mediante logs estructurados, activity persistida y metricas operativas, y ademas incorpora una estrategia ligera de recovery para documentos huerfanos en `PROCESSING` sin violar `single-flight` ni fabricar evidencia invalida.

El cambio se mantuvo incremental y revisable: se fortalecio el runtime existente sin introducir infraestructura ajena al foco del incremento ni romper la separacion entre domain, application y adapters.
