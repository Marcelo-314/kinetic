## 1. Propósito

Este SDD define el descenso implementable del servicio de procesamiento documental: módulos, componentes, interfaces, persistencia, runtime, adapters, límites transaccionales y estrategia de testing. El challenge exige una API REST para controlar procesos, procesamiento asíncrono real, procesamiento por lotes de archivos `.txt`, persistencia de estados, resultados y logs, y estados explícitos de proceso.

Este documento asume como ya decididos:

* arquitectura hexagonal estricta,
* implementación sobre Spring Boot,
* no uso de Spring Batch,
* máquina de estados propia en Java 21,
* runtime explícito con checkpoint seguro al cierre de documento,
* persistencia híbrida de estado, evidencia, snapshots y logs,
* failure policies configurables.

---

## 2. Objetivos de diseño

La implementación debe optimizar simultáneamente estas propiedades:

* claridad semántica del lifecycle,
* aislamiento de dominio respecto del framework,
* consistencia observable entre status, progreso y results,
* testabilidad alta del motor de transición,
* concurrencia disciplinada,
* complejidad proporcional al alcance del challenge.

No se optimiza en esta versión:

* máximo throughput por proceso,
* paralelismo intra-proceso,
* distribución multi-nodo sofisticada,
* restartability intra-documental,
* pipeline batch empresarial tipo ETL pesado.

---

## 3. Vista arquitectónica

### 3.1. Estilo

Arquitectura hexagonal, con cinco planos:

```text
[ inbound adapters ]
        |
[ application ]
        |
[ domain ]
        |
[ outbound ports ]
        |
[ outbound adapters ]
```

### 3.2. Regla de dependencia

Las dependencias deben apuntar hacia adentro:

* adapters dependen de aplicación,
* aplicación depende de dominio y puertos,
* dominio no depende de framework ni infraestructura.

### 3.3. Stack de marco

* **Framework base:** Spring Boot
* **Lenguaje:** Java 21
* **No usar:** Spring Batch
* **Motor de estados:** propio, basado en sealed interfaces + pattern matching
* **Runtime async:** explícito, no delegado a `@Async` como modelo principal

## 11. Diseño del runtime

### 11.1. Vista general

```text
Scheduler/Dispatcher
    -> claim process
    -> submit worker task
Worker
    -> load aggregate + flags + next document
    -> process one document
    -> close document
    -> update progress
    -> emit snapshot/result
    -> re-evaluate terminality
```

### 11.2. Dispatcher

Responsabilidades:

* buscar procesos `RUNNING` elegibles,
* respetar límite global de concurrencia,
* reclamar lease,
* despachar workers.

### 11.3. Lease manager

Debe ofrecer algo equivalente a:

```java
public interface ProcessLeasePort {
    boolean tryAcquire(ProcessId processId, String ownerId, Instant leaseUntil);
    boolean renew(ProcessId processId, String ownerId, Instant leaseUntil);
    void release(ProcessId processId, String ownerId);
}
```

### 11.4. Worker

Regla de ejecución por worker:

1. cargar proceso;
2. verificar flags de control;
3. si `stop_requested`, converger a `STOPPED`;
4. si `pause_requested`, converger a `PAUSED`;
5. tomar siguiente documento pendiente;
6. marcarlo `PROCESSING`;
7. procesarlo fuera de transacción;
8. cerrarlo `PROCESSED` o `FAILED`;
9. actualizar progreso;
10. emitir snapshot parcial;
11. evaluar completion/failure;
12. liberar lease o dejar listo para nuevo ciclo.

### 11.5. Single-flight

Nunca dos workers para el mismo proceso al mismo tiempo.

## 12. Transacciones

### 12.1. Fase A — preparación corta

Transacción corta para:

* reclamar proceso si corresponde,
* cargar estado/flags,
* seleccionar siguiente documento,
* marcar `PROCESSING`.

### 12.2. Fase B — trabajo fuera de transacción

* leer archivo,
* contar líneas/palabras/caracteres,
* calcular top words,
* generar summary extractivo.

### 12.3. Fase C — cierre corto

Transacción corta para:

* cerrar `DocumentExecution`,
* actualizar `ProgressSnapshot`,
* agregar `ActivityLogEntry`,
* emitir `ProcessResult` parcial,
* evaluar `CompleteProcess` / `FailProcess` / `FinalizeStoppedProcess`.

### 12.4. Regla

No se permite transacción larga cubriendo el análisis completo del documento.

## 15 bis. API Contract Source of Truth (OpenAPI)

La interfaz HTTP pública del servicio queda definida formalmente por la especificación **OpenAPI 3.1.0** aprobada para el proyecto. En consecuencia, este SDD no actúa como fuente primaria de verdad del contrato REST, sino como documento de diseño que explica cómo dicho contrato será implementado en la arquitectura del servicio. La especificación OpenAPI fija el `server` base `/api/v1`, los tags `Processes`, `Results` y `Activity`, y el catálogo completo de operaciones públicas del servicio. 

### 15 bis.1. Alcance contractual cubierto por OpenAPI

La OpenAPI aprobada cubre el contrato externo completo de la API pública, incluyendo:

* `POST /processes`
* `GET /processes`
* `POST /processes/{process_id}/authorize`
* `POST /processes/{process_id}/pause`
* `POST /processes/{process_id}/resume`
* `POST /processes/{process_id}/stop`
* `GET /processes/{process_id}/status`
* `GET /processes/{process_id}/results`
* `GET /processes/{process_id}/activity` 

### 15 bis.2. Regla de precedencia documental

Para la capa HTTP externa, la precedencia documental será la siguiente:

1. **OpenAPI** como fuente de verdad del contrato REST público.
2. **SDD** como fuente de verdad del diseño de implementación de ese contrato.
3. **Código** como materialización concreta, que deberá permanecer conforme tanto a OpenAPI como al SDD.

En caso de divergencia entre el texto descriptivo del SDD y el contrato OpenAPI, prevalece la especificación OpenAPI para todo lo relativo a rutas, parámetros, request bodies, response bodies, status codes y schemas públicos. 

### 15 bis.3. Implicancias para controllers y DTOs

Los controllers REST y sus DTOs de request/response deberán implementarse en correspondencia directa con los `paths`, `parameters`, `requestBody`, `responses` y `components/schemas` definidos por la OpenAPI. Esto incluye, como mínimo, los schemas `ProcessStatus`, `AuthorizationState`, `ResultKind`, `SelectionMode`, `SummaryPolicy`, `FailurePolicy`, `DocumentStatus`, `CreateProcessRequest`, `ProcessPlan`, `AuthorizationView`, `ProgressView`, `TerminalInfo`, `ProcessResource`, `CreateProcessResponse`, `CommandAcceptedResponse`, `ProcessStatusResponse`, `ProcessListItem`, `ProcessListResponse`, `WordFrequency`, `DocumentResult`, `ExcludedDocument`, `CoverageView`, `TotalsView`, `ProcessResultsResponse`, `ActivityItem`, `ActivityListResponse` y `ErrorResponse`. 

### 15 bis.4. Convenciones externas obligatorias

La implementación HTTP deberá respetar las convenciones fijadas por la OpenAPI aprobada:

* prefijo base `/api/v1`
* `process_id` como identificador canónico en path
* enums públicos exactamente como aparecen en la especificación
* estructura de errores basada en `ErrorResponse`
* responses tipadas según los schemas aprobados. 

### 15 bis.5. Status codes y errores

La implementación deberá respetar los status codes y envelopes de error definidos por OpenAPI para cada operación. En particular:

* `POST /processes` devuelve `201`
* `POST /processes/{process_id}/authorize|pause|resume|stop` devuelven `202`
* las queries devuelven `200`
* los errores públicos se expresan mediante `ErrorResponse` con estructura `error.code`, `error.message` y `error.details`. 

### 15 bis.6. Trazabilidad entre SDD y OpenAPI

El mapeo entre diseño e interfaz externa queda definido así:

* **Use cases de aplicación** ↔ `operationId` de OpenAPI
* **Controllers REST** ↔ `paths` de OpenAPI
* **DTOs externos** ↔ `components/schemas`
* **Error handling web** ↔ `ErrorResponse`
* **Tests de contrato Postman/Newman** ↔ validación ejecutable del contrato OpenAPI. 

### 15 bis.7. Regla de mantenimiento

Toda modificación futura del contrato REST deberá actualizar primero la especificación OpenAPI y luego, si corresponde, el SDD y la colección de pruebas de contrato. No deberá introducirse ni mantenerse comportamiento HTTP público que no esté representado en la OpenAPI aprobada.

## 16. Implementación de la máquina de estados

### 16.1. Opción recomendada

Un `TransitionEngine` central con pattern matching por command y por estado.

Ejemplo conceptual:

```java
public final class DefaultTransitionEngine implements TransitionEngine {

    @Override
    public TransitionResult apply(
        ProcessAggregate process,
        ProcessCommand command,
        TransitionContext context
    ) {
        return switch (process.state()) {
            case Pending pending -> applyPending(process, command, context);
            case Running running -> applyRunning(process, command, context);
            case Paused paused -> applyPaused(process, command, context);
            case Completed completed -> invalid(process, command);
            case Failed failed -> invalid(process, command);
            case Stopped stopped -> invalid(process, command);
        };
    }
}
```

### 16.2. Razón

* centraliza la matriz de transición,
* facilita test unitario exhaustivo,
* evita comportamiento disperso en muchas clases con framework coupling.

### 17.1. Control optimista

`Process.version` se usa para proteger:

* pause,

* stop,

* finalize stop.

### 17.2. Lease

`process_lease` o equivalente protege contra doble worker.

### 17.3. Precedencia terminal

Aplicar explícitamente esta precedencia al checkpoint:

```text
FAILED > STOPPED > COMPLETED > PAUSED
```

### 17.4. Precedencia de señales

Aplicar explícitamente:

```text

```

## 23. Secuencia end-to-end principal

### 23.1. Create + Authorize + Complete

```text
REST Create -> Application -> Orchestrator -> persist PENDING
REST Authorize -> Application -> Authorization + Orchestrator -> persist RUNNING
Dispatcher scans runnable process
Lease acquired
Worker selects next document
Worker marks PROCESSING
Worker analyzes document
Worker closes document
Progress updated
Partial result snapshotted
Loop until no pending docs
Orchestrator completes process
Final result snapshotted
REST Status/Results observe COMPLETED/FINAL
```

### 23.2. Pause / Resume

```text
REST Pause -> set pause_requested
Worker reaches document checkpoint
Orchestrator sets PAUSED
REST Resume -> clear pause_requested
Orchestrator sets RUNNING
Dispatcher/worker resumes processing
```

### 23.3. Stop

```text
REST Stop -> set stop_requested
Worker reaches document checkpoint
Orchestrator sets STOPPED
TerminalInfo persisted
Partial terminal result persisted
```

## 25. Riesgos principales

### 25.1.

Deriva de lógica de lifecycle hacia servicios Spring o controllers.

### 25.2.

Duplicación de verdad entre dominio y entidades persistentes.

### 25.3.

Runtime sin lease robusto -> doble worker.

### 25.4.

Snapshots construidos con documentos no cerrados.

### 25.5.

Transacciones demasiado largas.

### 25.6.

Confusión entre `COMPLETED` y “todos los documentos exitosos”, cuando bajo `TOLERATE_PARTIAL_FAILURES` no es lo mismo.
