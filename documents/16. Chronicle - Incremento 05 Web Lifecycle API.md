# Chronicle - Incremento 05 Web Lifecycle API

## Objetivo

Este incremento expone la capa web funcional del lifecycle básico y de las consultas `status` / `list`, refuerza la legibilidad del `ProcessPersistenceMapper` respecto del versionado dominio `<->` JPA, y enriquece `DocumentExecution` y `ProcessResult` para alinearlos mejor con el contrato futuro sin adelantar runtime ni results reales.

## Alcance implementado

### 1. Refuerzo de `ProcessPersistenceMapper`

Se revisó el mapper de `Process` para mantener la semántica actual de versionado sin aritmética inline opaca.

Se encapsuló la traducción entre:

- versión visible del dominio
- versión técnica de JPA/Hibernate

mediante helpers privados con nombres semánticos claros.

También se extendió la persistencia de `Process` para soportar los campos mínimos necesarios para el contrato web de `status` y `list`:

- `created_at`
- `updated_at`
- `objective`
- `result_kind`

## 2. Enriquecimiento mínimo de modelos satélite

### `ProcessResult`

- `totalWords`
- `totalLines`
- `totalCharacters`
- `mostFrequentWords`

Además se agregaron tipos mínimos de apoyo:

- `ResultKind`
- `DocumentStatus`
- `WordFrequency`
- `ExcludedDocument`
- `Coverage`

Estos cambios dejan el dominio mejor preparado para el siguiente paso de `results`, sin introducir todavía lógica real de análisis documental ni snapshots de resultados.

## 3. Ajuste mínimo del core para soportar web

Para exponer correctamente `GET /processes/{id}/status` y `GET /processes`, se extendió `ProcessAggregate` con:

- `createdAt`
- `updatedAt`
- `objective`
- `resultKind`

Y se agregó soporte de lectura en `ProcessRepository` para listar procesos.

El objetivo fue cubrir el contrato externo aprobado con el mínimo de datos persistidos necesarios, sin adelantar infraestructura de runtime.

## 4. Web layer funcional

Se implementó la capa web funcional con Spring Web MVC bajo `adapters.in.web`.

### Endpoints implementados

- `POST /api/v1/processes`
- `POST /api/v1/processes/{process_id}/authorize`
- `POST /api/v1/processes/{process_id}/pause`
- `POST /api/v1/processes/{process_id}/resume`
- `POST /api/v1/processes/{process_id}/stop`
- `GET /api/v1/processes/{process_id}/status`
- `GET /api/v1/processes`

### Características

- controllers delgados
- delegación a use cases de aplicación
- DTOs web separados del dominio y de `application.request`
- payloads externos en `snake_case`
- mapeo de errores consistente con `ErrorResponse`

## 5. DTOs web externos

Se agregaron DTOs externos alineados con OpenAPI para:

- `CreateProcessRequest`
- `CreateProcessResponse`
- `CommandAcceptedResponse`
- `ProcessStatusResponse`
- `ProcessListResponse`
- `ErrorResponse`

También se agregaron DTOs auxiliares alineados con schemas del contrato:

- `AuthorizationView`
- `ProgressView`
- `ProcessPlan`
- `TerminalInfo`
- `ProcessListItem`

## 6. Error handling global

Se implementó un `@RestControllerAdvice` para mapear de forma consistente:

- `404` para proceso inexistente
- `409` para transición inválida
- `400` para request inválido
- `422` para invalidación semántica
- `500` para error inesperado

Con envelope:

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "details": {}
  }
}
```

## 7. Query use cases

Se agregaron use cases y views de aplicación para soportar la capa web sin acoplarla a persistencia:

- `GetProcessStatusUseCase`
- `ListProcessesUseCase`

Y modelos de lectura:

- `ProcessStatusView`
- `ProcessListItemView`
- `ProcessListView`
- `ListProcessesQuery`

Con esto, la web sigue dependiendo de application y no de repositorios concretos.

## 8. Composición Spring

Se agregó configuración explícita para los beans de aplicación y puertos técnicos reutilizados por la web:

- `ClockPort`
- `IdGeneratorPort`
- `TransitionEngine`
- use cases

También se agregó `LocalFileSourceAdapter` como implementación concreta del puerto de filesystem para el flujo actual de creación.

## 9. Qué no se implementó todavía

Se respetaron explícitamente estas restricciones:

- no runtime dispatcher real
- no lease manager real
- no workers
- no procesamiento documental real
- no `GET /api/v1/processes/{id}/results` completo
- no `GET /api/v1/processes/{id}/activity` completo
- no Spring Batch
- no Spring State Machine
- no lógica de lifecycle en controllers
- no entidades JPA como modelo de dominio

## Resultado

El proyecto queda con una API web funcional para el lifecycle básico y para las consultas `status` / `list`, alineada con la OpenAPI aprobada como fuente de verdad del contrato HTTP público.

Además, el core queda mejor preparado para los próximos incrementos gracias a:

- versionado más legible y semántico en persistencia
- modelos satélite enriquecidos para `results`
- separación clara entre dominio, application, web y persistencia

Este incremento sigue siendo incremental y revisable, sin adelantar runtime ni resultados analíticos completos.
