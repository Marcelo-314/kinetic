# Chronicle - Incremento 04 Persistence Adapters

## Objetivo

Este incremento implementa la persistencia real mínima del sistema usando Spring Data JPA sobre H2 in-memory, manteniendo la arquitectura hexagonal acordada y sin introducir todavía web funcional ni runtime real.

Además corrige dos derivas detectadas en el incremento anterior:

- renombre de `application.dto` a `application.request` para requests internos de use cases
- refinamiento de `ActivityLogEntry` para dejarlo mejor preparado para el contrato futuro

## Alcance implementado

### 1. Ajuste de naming en application

Se renombró el package:

- de `com.chronicle.application.dto`
- a `com.chronicle.application.request`

Se movieron:

- `CreateProcessRequest`
- `ProcessCommandRequest`

Y se actualizaron imports y tests para reflejar el cambio, sin crear todavía DTOs web.

### 2. Refinamiento mínimo de modelos satélite

Se enriqueció `ActivityLogEntry` con:

- `metadata`
- `correlationId`

El modelo se mantuvo simple y orientado a uso inmediato. Los use cases actuales fueron ajustados para persistir actividades con esa información.

## Persistencia JPA implementada

Se agregaron entidades JPA separadas del dominio para:

- `ProcessAggregate`
- `ProcessPlan`
- `AuthorizationInfo`
- `ProgressSnapshot`
- `ExecutionControlFlags`
- `TerminalInfo`
- `ActivityLogEntry`

Las entidades viven en:

- `com.chronicle.adapters.out.persistence.entity`

Se agregaron mappers explícitos dominio `<->` persistencia en:

- `com.chronicle.adapters.out.persistence.mapper`

Y repositorios Spring Data en:

- `com.chronicle.adapters.out.persistence.springdata`

Con esto se mantuvo la regla arquitectónica de no poner JPA dentro del dominio ni usar entidades JPA como modelo canónico.

## Adapters concretos de persistencia

Se implementaron adapters para los puertos actualmente usados por la aplicación:

- `ProcessRepository`
- `ProcessPlanRepository`
- `AuthorizationInfoRepository`
- `ProgressSnapshotRepository`
- `ExecutionControlFlagsRepository`
- `TerminalInfoRepository`
- `ActivityLogRepository`

Los adapters quedaron ubicados en:

- `com.chronicle.adapters.out.persistence`

`DocumentExecutionRepository` y `ProcessResultRepository` no se sobre-implementaron en este incremento porque todavía no son necesarios para los use cases actuales.

## Versionado y optimistic locking

Se implementó optimistic locking para `Process` con `@Version` en persistencia.

Como el dominio ya expone una semántica de `version` iniciando en `1`, se resolvió explícitamente la traducción entre:

- versión visible del dominio
- versión técnica usada por JPA/Hibernate para locking

Esto permitió:

- preservar el contrato actual del dominio
- mantener locking optimista real en persistencia
- evitar acoplar el dominio a decisiones internas de JPA

## Configuración Spring Boot / JPA

Se mantuvo H2 in-memory y una configuración simple.

También se ajustó el bootstrap para escanear correctamente:

- entidades JPA
- repositorios Spring Data

No se introdujeron migraciones ni complejidad adicional en esta etapa.

## Tests agregados

Se agregó un test de integración de persistencia con Spring Boot / JPA para verificar:

- guardado y carga de `ProcessAggregate`
- guardado y carga de `ProcessPlan`
- guardado y carga de `AuthorizationInfo`
- guardado y carga de `ProgressSnapshot`
- guardado y carga de `ExecutionControlFlags`
- guardado y carga de `TerminalInfo`
- guardado y carga de `ActivityLogEntry` con `metadata` y `correlationId`
- funcionamiento de optimistic locking en `Process`
- compatibilidad de los use cases actuales con los adapters reales de persistencia

## Validación

Verificación realizada:

```bash
mvn test
```

Resultado:

- `46` tests pasando

## Restricciones respetadas

En este incremento no se implementó:

- controllers REST funcionales
- DTOs web
- runtime dispatcher real
- lease manager real
- workers
- Spring Batch
- Spring State Machine

Tampoco se introdujo:

- JPA dentro del dominio
- lógica de lifecycle en entidades de persistencia
- sobre-implementación prematura de `DocumentExecution` o `ProcessResult`

## Resultado

El proyecto queda preparado para que los use cases actuales trabajen contra persistencia real sobre H2/JPA, conservando:

- dominio puro
- capa application desacoplada
- adapters concretos encapsulados en `adapters.out.persistence`

Este incremento deja una base persistente mínima, coherente y revisable para avanzar luego con web, runtime y snapshots/resultados más completos.
