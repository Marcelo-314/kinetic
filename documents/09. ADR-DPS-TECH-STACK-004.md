## 1. Contexto

El servicio ya tiene fijados:

* arquitectura hexagonal,
* máquina de estados propia en Java 21,
* runtime explícito con claim/lease y checkpoint al cierre de documento,
* persistencia híbrida de estado, evidencia, snapshots y logs,
* implementación sobre Spring Boot,
* exclusión explícita de Spring Batch.

Lo que resta decidir es el stack técnico concreto para implementar ese diseño con el menor costo accidental posible y con la mayor claridad defendible frente al challenge, cuyo foco principal está en arquitectura, API, concurrencia, manejo de errores y procesamiento asíncrono observable. 

---

## 2. Problema a resolver

Debemos fijar:

* framework base,
* modelo web,
* persistencia concreta,
* base de datos,
* strategy de migrations,
* modelo de ejecución async,
* toolchain de testing y validación de contrato.

La elección debe favorecer:

* claridad de implementación,
* velocidad de desarrollo,
* buena trazabilidad,
* mínima fricción con el diseño aprobado,
* y ausencia de frameworks innecesarios.

---

## 3. Decisión

## 3.1. Stack adoptado

El stack técnico adoptado para esta versión será:

* **Java 21**
* **Spring Boot 3.x**
* **Spring Web MVC**
* **Spring Data JPA**
* **H2 in-memory**
* **Hibernate / JPA** como implementación ORM
* **Virtual Threads de Java 21** para workers
* **Postman + Newman** para tests de contrato/aceptación
* **JUnit 5 + Mockito** para tests unitarios y de aplicación
* **Maven** como build tool

## 3.2. Exclusiones explícitas

No se utilizará:

* **Spring Batch**
* **Spring State Machine**
* **WebFlux/Reactor** como modelo principal
* **Event sourcing**
* **colas externas** como RabbitMQ/Kafka
* **PostgreSQL** u otra base persistente duradera en esta versión

---

## 4. Decisiones por componente

## 4.1. Lenguaje y runtime

### Decisión

La implementación DEBE realizarse en **Java 21**.

### Justificación

Porque Java 21 habilita directamente varias decisiones ya aprobadas:

* sealed interfaces,
* pattern matching,
* records,
* virtual threads.

Eso reduce muchísimo el costo sintáctico de la máquina de estados y del runtime.

---

## 4.2. Framework base

### Decisión

La implementación DEBE usar **Spring Boot 3.x**.

### Uso permitido

Spring Boot se usará para:

* bootstrap,
* configuración,
* wiring,
* controllers,
* transacciones,
* integración con persistencia,
* scheduler/disparadores.

### Uso no permitido

Spring Boot NO será dueño de:

* lifecycle del proceso,
* máquina de estados,
* runtime de dominio,
* semántica de commands.

---

## 4.3. Modelo web

### Decisión

La API HTTP se implementará con **Spring Web MVC**.

### Justificación

No necesitamos streaming reactivo ni un modelo no bloqueante extremo.
El servicio es principalmente:

* request/response,
* commands de control,
* queries de estado/resultados,
* más un runtime interno en background.

Web MVC encaja mejor con el estilo imperativo y con el uso de virtual threads.

---

## 4.4. Persistencia de dominio

### Decisión

La capa de persistencia se implementará con **Spring Data JPA** y mapeo explícito dominio ↔ persistencia.

### Regla

Las entidades JPA NO serán el modelo de dominio.
Serán artefactos del adapter de persistencia.

### Justificación

Esto mantiene la disciplina hexagonal y reduce el trabajo mecánico de acceso a datos.

---

## 4.5. Base de datos

### Decisión

La base de datos de esta versión será **H2 in-memory**.

### Alcance de la decisión

H2 in-memory será la única base de datos objetivo en esta versión del proyecto.

### Justificación favorable

* minimiza setup,
* acelera iteración,
* simplifica demo y evaluación,
* reduce fricción de entorno,
* encaja muy bien con una entrega de challenge y con tests automatizados.

### Observación crítica

Esta decisión tiene un costo real:

> la información persistida se pierde al reiniciar el proceso.

Eso significa que, en sentido estricto, la persistencia queda acotada a la vida del servicio en ejecución. Para el challenge esto puede seguir siendo aceptable si la demostración se realiza dentro de una única sesión operativa, pero no debe confundirse con persistencia durable de entorno real. El enunciado exige persistencia semántica de estados/resultados/logs, no necesariamente una tecnología durable específica; aun así, H2 in-memory reduce el alcance práctico de esa persistencia. 

### Consecuencia

La demo y los tests deben asumir que:

* el estado del servicio no sobrevive reinicios,
* la recuperación tras restart no será demostrable en esta versión,
* la persistencia observable se validará dentro de la sesión de ejecución.

---

## 4.6. Migrations

### Decisión

No se adopta Flyway ni Liquibase como requisito de esta versión.

### Justificación

Con H2 in-memory para un challenge de este alcance, agregar migrations formales introduce más ceremonias que valor.

### Regla

El esquema puede inicializarse por:

* DDL generado por Hibernate para entorno local/challenge,
* o scripts SQL de bootstrap simples si se quiere mayor control.

### Observación crítica

Para continuidad posterior del proyecto, esta decisión debería revisarse.

---

## 4.7. Runtime asíncrono

### Decisión

El runtime se implementará con:

* scheduler/disparador interno,
* semáforo o límite explícito de concurrencia,
* executor de **virtual threads**,
* claim/lease persistido por proceso.

### Justificación

Es el mejor match con el modelo ya aprobado:

* imperative style,
* blocking-friendly,
* simple de razonar,
* compatible con Spring MVC.

### Regla

Las virtual threads NO reemplazan:

* lease,
* optimistic locking,
* precedencias terminales,
* disciplina de transición.

---

## 4.8. Testing

### Decisión

La estrategia de testing adoptada será:

* **JUnit 5** para tests unitarios y de aplicación,
* **Mockito** para dobles de puertos cuando convenga,
* **Spring Boot Test** para integración selectiva,
* **Postman + Newman** para aceptación/contrato.

### Justificación

Esto cubre los cuatro niveles que importan aquí:

1. dominio puro,
2. casos de uso,
3. integración HTTP/persistencia,
4. contrato observable del servicio.

---

## 4.9. Build tool

### Decisión

Se usará **Maven**.

### Justificación

Es totalmente suficiente para este stack, encaja bien con Spring Boot y reduce fricción frente a una entrega estándar Java.

## 6. Alternativas consideradas y descartadas

## 6.1. PostgreSQL

### Descartada en esta versión

Razón:

* más setup,
* más fricción de entorno,
* menos velocidad para una PoC/challenge.

### Observación

Sería la candidata natural para la siguiente iteración seria del proyecto.

## 6.2. Spring Batch

### Descartada

Razón:

* duplicación de lifecycle,
* sobrecarga técnica innecesaria,
* no alineada con el modelo de dominio ya fijado. 

## 6.3. Spring State Machine

### Descartada

Razón:

* innecesaria para una máquina de estados ya perfectamente expresable en Java 21.

## 6.4. WebFlux/Reactor

### Descartada

Razón:

* complejidad innecesaria,
* menor alineación con el modelo imperativo,
* no hay necesidad clara de modelo reactivo end-to-end.

## 6.5. Flyway/Liquibase

### Descartadas por ahora

Razón:

* costo accidental innecesario con H2 in-memory para este alcance.

---

## 7. Consecuencias positivas

Esta elección de stack aporta:

### 7.1.

Implementación limpia y muy entendible.

### 7.2.

Excelente alineación con la arquitectura hexagonal fijada.

### 7.3.

Bajo costo de bootstrap y demo.

### 7.4.

Muy buena testabilidad del dominio y de la API.

### 7.5.

Compatibilidad muy natural con Postman/Newman.

---

## 8. Costos y trade-offs

## 8.1. H2 in-memory no da persistencia durable

Éste es el trade-off principal y más importante.

## 8.2. Sin migrations formales, el esquema queda menos gobernado

Aceptable para esta versión, pero no ideal a mediano plazo.

## 8.3. JPA agrega algo de ceremony

Aceptable porque reduce muchísimo trabajo de repositorios y queries base.

## 8.4. Virtual threads no resuelven semántica de concurrencia

Solo ayudan con ejecución.

---

## 9. Reglas normativas finales

### 9.1.

La implementación DEBE usar Java 21.

### 9.2.

La implementación DEBE usar Spring Boot 3.x y Spring Web MVC.

### 9.3.

La persistencia DEBE implementarse con Spring Data JPA sobre H2 in-memory en esta versión.

### 9.4.

La implementación NO DEBE usar Spring Batch.

### 9.5.

La implementación NO DEBE usar Spring State Machine.

### 9.6.

La ejecución asíncrona DEBE apoyarse en un runtime explícito y puede usar virtual threads con límite de concurrencia.

### 9.7.

La verificación de contrato DEBE apoyarse en la colección Postman y su ejecución con Newman.

---

Con este ADR queda cerrado el marco técnico completo de implementación.

* modelo de dominio,
* flujo de commands/queries,
* runtime,
* persistencia,
* failure policy,
* arquitectura,
* y stack.
