# Chronicle - Incremento 11 Automatic Schema Initialization

## Objetivo

Este incremento habilita la inicializacion automatica del esquema de base de datos al arranque del servicio mediante `schema.sql`, manteniendo control explicito del modelo relacional y evitando cualquier paso manual para dejar Chronicle operativo sobre H2 in-memory.

## Alcance implementado

## 1. Inicializacion automatica del esquema

Se agrego `src/main/resources/schema.sql` como definicion explicita del esquema de base de datos.

### Cobertura del esquema

El script incluye las estructuras actualmente necesarias para el estado real del servicio:

- `process`
- `process_plan`
- `authorization_info`
- `progress_snapshot`
- `execution_control_flags`
- `terminal_info`
- `document_execution`
- `process_result`
- `activity_log`
- `process_lease`

No se agregaron tablas especulativas ni estructuras no usadas por la implementacion actual.

## 2. Definicion explicita de tablas, constraints e indices

El `schema.sql` define:

- claves primarias
- foreign keys entre tablas relacionadas
- unicidades necesarias por proceso
- versionado para optimistic locking en `process` y `process_lease`
- columnas requeridas por `results`, `activity` y runtime
- indices minimos utiles para queries reales del sistema

### Indices relevantes incluidos

- busqueda de procesos `RUNNING` por `updated_at`
- busqueda de documentos por `process_id` y `document_status`
- busqueda de activity por `process_id`, `event_type` y `timestamp`
- busqueda de snapshots de results por `process_id` y `computed_at`
- soporte de lease por expiracion

## 3. Politica de esquema

Se dejo una politica clara y controlada:

- `schema.sql` gobierna la creacion del esquema
- Spring ejecuta ese script automaticamente al iniciar
- Hibernate deja de ser responsable principal de crear tablas
- JPA pasa a validar compatibilidad del mapeo contra el esquema existente

### Configuracion aplicada

En `application.yaml` se ajusto:

- `spring.sql.init.mode=always`
- `spring.jpa.hibernate.ddl-auto=validate`

### Resultado

Chronicle arranca con una base lista para operar sin consola H2, sin ejecucion manual de scripts y sin depender de `create` o `create-drop` como estrategia principal.

## 4. Compatibilidad con el estado actual del proyecto

Se verifico que el esquema explicito sea compatible con:

- entidades JPA actuales
- adapters de persistencia actuales
- runtime con dispatcher, worker, lease y recovery
- web actual
- proyecciones de `results`
- `activity` con `metadata` y `correlation_id`

### Puntos revisados

- tipos de columnas
- claves primarias
- foreign keys
- unicidades por `process_id`
- columnas de optimistic locking
- tablas de lease y document execution

## 5. Arranque autonomo del servicio

Con este incremento, al levantar Chronicle:

- se crea automaticamente el esquema en H2 in-memory
- la aplicacion valida sus entidades JPA contra ese esquema
- el servicio queda listo para crear procesos y operar sin preparacion manual adicional

## 6. Tests agregados

Se agrego `AutomaticSchemaInitializationIntegrationTest`.

### Cobertura

- el contexto Spring arranca usando la configuracion real de `schema.sql`
- las tablas principales existen automaticamente tras el arranque
- los adapters y use cases pueden operar sobre la base inicializada
- se puede crear un proceso sin preparar la base manualmente

## 7. Documentacion minima

Se actualizo `README.md` para dejar explicito:

- que Chronicle crea automaticamente el esquema al arrancar
- que ya no hace falta ejecutar nada manualmente para inicializar la base
- que la consola H2 queda disponible solo para inspeccion opcional

## 8. Que no se implemento

Se mantuvo el alcance acotado del incremento:

- no se introdujeron migraciones con Flyway o Liquibase
- no se reestructuro el dominio
- no se cambio la arquitectura
- no se agregaron seeds innecesarios
- no se tocaron funcionalidades no relacionadas


Resultado:

## Resultado

Chronicle queda ahora completamente autonomo respecto de la inicializacion de su base H2 in-memory: el esquema se crea automaticamente al arranque, queda bajo control explicito mediante `schema.sql` y el servicio puede operar sin pasos manuales ni dependencia de creacion opaca por Hibernate.

El cambio se mantuvo pequeno y revisable, alineado con la arquitectura hexagonal actual y con la decision de mantener una politica de esquema clara, explicita y coherente con el estado real del proyecto.
