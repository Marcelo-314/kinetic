# Chronicle - Incremento 12 Idle Runtime Telemetry Noise Reduction

## Objetivo

Este incremento reduce el ruido de telemetria del runtime cuando Chronicle esta idle, sin cambiar la semantica funcional del dispatcher, del scheduler ni del runtime. El foco fue mantener visibles los eventos operativamente relevantes y dejar de inundar `INFO` con scans vacios repetitivos.

## Alcance implementado

## 1. Reduccion de ruido en logs idle

Se reviso la telemetria del dispatcher y se ajusto la politica de logging para scans sin trabajo real.

### Politica implementada

- `dispatcher_scan_start` ya no se emite en `INFO`
- `dispatcher_scan_start` se registra en `DEBUG`
- `dispatcher_scan_end` se mantiene en `INFO` solo cuando hubo actividad relevante
- si `scanned_processes = 0` y `dispatched_processes = 0`, `dispatcher_scan_end` se degrada a `DEBUG`

### Resultado

Cuando el scheduler sigue corriendo pero no existen procesos para despachar:

- Chronicle ya no genera spam repetitivo en `INFO`
- el runtime sigue haciendo sus scans normalmente
- la telemetria tecnica sigue disponible en `DEBUG`

## 2. Eventos relevantes conservados en INFO

No se degrado la visibilidad de los eventos importantes del runtime.

### Permanecen en `INFO`

- `LEASE_ACQUIRED`
- `LEASE_RENEWED`
- `LEASE_RENEWAL_FAILED`
- `WORKER_STARTED`
- `WORKER_ABORTED`
- `DOCUMENT_PROCESSING_STARTED`
- `DOCUMENT_PROCESSED`
- `DOCUMENT_FAILED`
- `PROCESS_PAUSED`
- `PROCESS_STOPPED`
- `PROCESS_COMPLETED`
- `PROCESS_FAILED`
- `CHECKPOINT_RESOLVED`
- `RUNTIME_RECOVERY_APPLIED`

## 3. Comportamiento funcional intacto

El ajuste fue puramente observacional.

### No cambia

- scheduler
- dispatcher
- lease
- worker
- recovery
- semantica de dispatch
- metricas existentes
- activity persistida

Las metricas y el comportamiento real del runtime siguen funcionando igual; solo se recalibro el nivel de log de los scans vacios.

## 4. Encapsulacion del criterio en RuntimeTelemetry

La politica quedo concentrada en `RuntimeTelemetry`, evitando logica dispersa o implicita en el dispatcher.

### Ajuste realizado

Se agrego un helper semantico para distinguir un dispatch scan idle:

- `isIdleDispatchScan(int scanned, int dispatched)`

Con esto queda explicito en el codigo por que un scan vacio no debe generar ruido en `INFO`.

## 5. Tests agregados

Se incorporo `RuntimeTelemetryTest`.

### Cobertura

- scans vacios no emiten logs `INFO`
- scans vacios siguen dejando traza en `DEBUG`
- eventos operativamente relevantes siguen siendo visibles en `INFO`

Ademas se verifico que:

- no se altera el comportamiento funcional del dispatcher al no haber trabajo
- no se rompen metricas ni activity

## 6. Documentacion minima

Se actualizo `README.md` con una nota breve de observabilidad:

- los scans vacios del dispatcher no se emiten en `INFO`
- los eventos relevantes del runtime siguen visibles en `INFO`

## 7. Que no se implemento

Se mantuvo el alcance corto y acotado del incremento:

- no se cambio arquitectura
- no se rehizo el runtime
- no se tocaron reglas de negocio
- no se introdujeron frameworks nuevos
- no se toco OpenAPI
- no se hizo una refactorizacion grande

## 8. Validacion

Verificacion ejecutada:

```bash
mvn test
```

Resultado:

- `75` tests pasando

## Resultado

Chronicle queda ahora mucho menos ruidoso en estado idle: el scheduler puede seguir escaneando periodicamente sin inundar `INFO` con eventos vacios repetitivos. Al mismo tiempo, los eventos de runtime que realmente importan para operacion y diagnostico siguen visibles con el mismo nivel de severidad.

El cambio se mantuvo pequeno, revisable y semantica-funcionalmente neutro: se ajusto la calibracion observacional del runtime sin tocar su comportamiento real.
