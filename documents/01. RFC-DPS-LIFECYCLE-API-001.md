
# RFC-DPS-LIFECYCLE-API-001

**Título:** Process Lifecycle and API Semantics
**Versión:** v0.1-draft
**Estado:** Draft
**Ámbito:** Document Processing Service
**Idioma normativo:** español

## 1. Propósito

Este RFC fija la semántica canónica del servicio de procesamiento documental: qué es un proceso, cuáles son sus estados, qué transiciones son válidas, qué significa cada operación pública de la API y cómo debe interpretarse la disponibilidad de resultados durante el ciclo de vida. El challenge base exige una REST API con operaciones de inicio, detención, consulta de estado, listado y recuperación de resultados; además exige procesamiento asíncrono real, procesamiento por lotes de archivos `.txt`, persistencia de estados/resultados/logs y el uso explícito de los estados `PENDING`, `RUNNING`, `PAUSED`, `COMPLETED`, `FAILED` y `STOPPED`. 

Este RFC toma ese núcleo y cierra dos tensiones del enunciado original:

1. da entidad operativa real a `PENDING`;
2. vuelve plenamente operable a `PAUSED` mediante `pause/resume`.
   La justificación es que el documento enumera esos estados como parte del modelo base, pero deja subespecificadas sus transiciones y su semántica externa. 

## 2. Alcance

Este RFC **sí** define:

* el lifecycle del proceso;
* la semántica observable de la API;
* la semántica de resultados `NONE / PARTIAL / FINAL`;
* las invariantes mínimas del proceso;
* las reglas de terminalidad;
* la semántica de error a nivel de contrato.

Este RFC **no** define:

* stack tecnológico;
* clases concretas o estructura de paquetes;
* esquema físico de persistencia;
* algoritmos concretos de summary;
* tuning de concurrencia o estrategia de hilos;
* detalles de despliegue.

## 3. Motivación y lectura del challenge

El challenge no pide simplemente “analizar textos”, sino un servicio que administre procesos asíncronos observables por API, con estados persistidos, resultados recuperables y control operacional explícito. El peso de evaluación asignado a arquitectura, implementación de API, concurrencia, calidad de código y manejo de errores confirma que el problema principal es de lifecycle y consistencia operacional, más que de sofisticación algorítmica del análisis textual. 

Por lo tanto, el contrato canónico del servicio debe priorizar:

* separación entre plano de control y plano de trabajo;
* modelo explícito de estados y transiciones;
* consistencia entre estado, progreso y resultados;
* capacidad de observación y control sin ambigüedad semántica. 

## 4. Conceptos canónicos

### 4.1. Process

Un **Process** es la unidad top-level expuesta por la API. Representa una corrida de análisis documental con identidad propia, lifecycle persistido y resultados observables.

### 4.2. Process Plan

Un **Process Plan** es la definición congelada del trabajo a ejecutar: carpeta fuente, criterio de selección de documentos, cardinalidad esperada, tamaño de batch y políticas de procesamiento.

### 4.3. Document Execution

Una **Document Execution** es la unidad mínima de evidencia analítica. Representa el tratamiento de un documento individual dentro de un proceso.

### 4.4. Batch

Un **Batch** es una unidad operacional de planificación y ejecución que agrupa documentos.

### 4.5. Process Result

Un **Process Result** es una proyección agregada de la evidencia documental disponible en un momento dado.

## 5. Modelo de estados del proceso

El estado canónico de un proceso DEBE pertenecer al conjunto:

```text
PENDING | RUNNING | PAUSED | COMPLETED | FAILED | STOPPED
```

Este conjunto proviene del challenge base. 

### 5.1. `PENDING`

`PENDING` significa:

> proceso creado, con alcance definido y persistido, todavía no despachado al runtime por falta de autorización operacional.

Esta definición es una decisión de este RFC. Se adopta para dar significado real al estado `PENDING`, que en el challenge aparece definido como “created but not started”, aunque el set de endpoints base no distingue claramente entre creación y ejecución. 

### 5.2. `RUNNING`

`RUNNING` significa:

> proceso autorizado y en ejecución efectiva, elegible para consumir batches y producir evidencia documental.

### 5.3. `PAUSED`

`PAUSED` significa:

> proceso previamente activo, suspendido de forma ordenada, que conserva identidad, progreso y resultados parciales, y que no consume nuevos batches mientras permanezca en este estado.

### 5.4. `COMPLETED`

`COMPLETED` significa:

> proceso terminado exitosamente, con cierre normal del plan de trabajo y disponibilidad de resultado final consolidado.

### 5.5. `FAILED`

`FAILED` significa:

> proceso terminado por error terminal no recuperable, con snapshot parcial terminal si existía evidencia previa.

### 5.6. `STOPPED`

`STOPPED` significa:

> proceso terminado por orden externa de control, no por error interno.

## 6. Clasificación de estados

Los estados se clasifican así:

* **no terminales**: `PENDING`, `RUNNING`, `PAUSED`
* **terminales**: `COMPLETED`, `FAILED`, `STOPPED`

Los estados terminales DEBEN ser absorbentes.

## 7. Transiciones válidas

Las únicas transiciones válidas del lifecycle canónico son las siguientes:

| Origen    | Destino     | Condición                                               |
| --------- | ----------- | ------------------------------------------------------- |
| `PENDING` | `RUNNING`   | autorización aceptada y despacho al runtime             |
| `PENDING` | `STOPPED`   | cancelación antes de ejecución                          |
| `PENDING` | `FAILED`    | imposibilidad estructural terminal posterior a creación |
| `RUNNING` | `PAUSED`    | pausa aceptada y alcanzado checkpoint seguro            |
| `RUNNING` | `COMPLETED` | cierre exitoso del plan                                 |
| `RUNNING` | `FAILED`    | error terminal                                          |
| `RUNNING` | `STOPPED`   | stop aceptado y alcanzado checkpoint seguro             |
| `PAUSED`  | `RUNNING`   | resume aceptado                                         |
| `PAUSED`  | `STOPPED`   | cancelación desde pausa                                 |

Toda transición no listada arriba DEBE rechazarse como inválida.

## 8. Reglas de terminalidad

### 8.1.

`COMPLETED`, `FAILED` y `STOPPED` DEBEN ser estados absorbentes.

### 8.2.

Un proceso terminal NO DEBE aceptar `authorize`, `pause`, `resume` ni `stop`.

### 8.3.

La terminación terminal DEBE quedar acompañada por información causal suficiente para distinguir:

* cierre normal;
* detención manual;
* fallo terminal.

## 9. Semántica pública de la API

El challenge base exige cinco operaciones externas: start, stop, status, list y results. Este RFC conserva ese núcleo y agrega authorize, pause y resume para cerrar el lifecycle de forma coherente. 

## 9.1. Create Process

**Operación canónica:** `POST /api/v1/processes`
**Compatibilidad challenge:** `POST /process/start`

Semántica:

> crea un proceso en `PENDING`, con plan congelado y sin iniciar aún la ejecución documental.

La operación de creación DEBE:

* persistir identidad del proceso;
* fijar el plan;
* inicializar progreso en cero;
* crear el estado de autorización correspondiente.

La operación de creación NO DEBE iniciar análisis documental.

## 9.2. Authorize Process

**Operación canónica:** `POST /api/v1/processes/{id}/authorize`

Semántica:

> concede autorización operacional y despacha el proceso al runtime.

`Authorize Process` SOLO DEBE aceptarse cuando el estado actual sea `PENDING`.

## 9.3. Pause Process

**Operación canónica:** `POST /api/v1/processes/{id}/pause`

Semántica:

> solicita la suspensión ordenada de un proceso activo.

`Pause Process` SOLO DEBE aceptarse en `RUNNING`.

La aceptación del comando y la convergencia estable a `PAUSED` PUEDEN no ser instantáneas. El sistema PUEDE completar la unidad mínima en curso antes de fijar el estado `PAUSED`.

## 9.4. Resume Process

**Operación canónica:** `POST /api/v1/processes/{id}/resume`

Semántica:

> reanuda un proceso pausado y lo vuelve elegible para ejecución.

`Resume Process` SOLO DEBE aceptarse en `PAUSED`.

## 9.5. Stop Process

**Operación canónica:** `POST /api/v1/processes/{id}/stop`
**Compatibilidad challenge:** `POST /process/stop/{process_id}`

Semántica:

> detiene administrativamente el proceso.

`Stop Process` DEBE aceptarse únicamente en:

* `PENDING`
* `RUNNING`
* `PAUSED`

`Stop Process` NUNCA DEBE materializarse como `FAILED`.

## 9.6. Get Process Status

**Operación canónica:** `GET /api/v1/processes/{id}/status`
**Compatibilidad challenge:** `GET /process/status/{process_id}`

Semántica:

> devuelve la vista operativa canónica del proceso.

Esta operación DEBE ser la fuente de verdad del lifecycle observable.
NO DEBE recalcular analítica pesada.

## 9.7. List Processes

**Operación canónica:** `GET /api/v1/processes`
**Compatibilidad challenge:** `GET /process/list`

Semántica:

> devuelve un catálogo resumido de procesos y su estado actual.

## 9.8. Get Process Results

**Operación canónica:** `GET /api/v1/processes/{id}/results`
**Compatibilidad challenge:** `GET /process/results/{process_id}`

Semántica:

> devuelve la proyección analítica vigente del proceso.

Esta operación DEBE distinguir entre ausencia de evidencia, resultado parcial y resultado final consolidado.

## 10. Semántica de resultados

El challenge exige resultados de análisis, incluyendo estadísticas básicas, palabras frecuentes y summary. Este RFC fija además la semántica de disponibilidad de esos resultados a lo largo del lifecycle. 

### 10.1. Tipos de resultado

El tipo canónico de resultado DEBE pertenecer al conjunto:

```text
NONE | PARTIAL | FINAL
```

### 10.2. `NONE`

`NONE` significa:

> no existe evidencia analítica consolidada todavía.

### 10.3. `PARTIAL`

`PARTIAL` significa:

> existe evidencia analítica consolidada para un subconjunto del plan, pero no existe cierre exitoso total del proceso.

### 10.4. `FINAL`

`FINAL` significa:

> existe un resultado consolidado canónico correspondiente a un proceso exitosamente completado.

## 11. Correspondencia entre estado y tipo de resultado

La correspondencia canónica es:

* `PENDING -> NONE`
* `RUNNING -> PARTIAL` cuando ya exista evidencia procesada; antes de eso PUEDE observarse `NONE` en una ventana transitoria muy inicial
* `PAUSED -> PARTIAL`
* `STOPPED -> PARTIAL`
* `FAILED -> PARTIAL`
* `COMPLETED -> FINAL`

Un proceso `COMPLETED` NUNCA DEBE exponer `NONE` ni `PARTIAL` como resultado canónico vigente.

## 12. Evidencia documental y agregación

### 12.1.

La unidad mínima de evidencia analítica DEBE ser el documento individual procesado.

### 12.2.

Todo agregado de resultados DEBE construirse a partir de evidencia documental cerrada.

### 12.3.

El servicio NO DEBE presentar como procesado un documento cuya ejecución documental no haya finalizado.

### 12.4.

Los documentos fallidos PUEDEN aparecer en el detalle del proceso, pero NO DEBEN contaminar los agregados analíticos de éxito.

### 12.5.

El resultado final consolidado SOLO DEBE emitirse cuando el proceso esté en `COMPLETED`.

## 13. Política de summary

El challenge exige “generate a content summary”, pero no define método ni criterio de aceptación. Este RFC fija la siguiente postura: 

### 13.1.

El summary documental DEBE ser determinista.

### 13.2.

La política canónica inicial DEBE ser extractiva.

### 13.3.

El servicio PUEDE construir un summary global del proceso, pero ese summary global SOLO DEBE considerarse canónico cuando el resultado sea `FINAL`.

## 14. Progreso e invariantes cuantitativas

El challenge muestra explícitamente una estructura de progreso con `total_files`, `processed_files`, `percentage`, `started_at` y `estimated_completion`. Este RFC fija las siguientes invariantes. 

### 14.1.

`processed_files <= total_files`

### 14.2.

El progreso observable NO DEBE decrecer.

### 14.3.

`pending_files = total_files - processed_files`

### 14.4.

`successful_files + failed_files <= processed_files`

### 14.5.

En `PENDING`, `processed_files` DEBE ser cero.

### 14.6.

En `COMPLETED`, el progreso observable DEBE ser consistente con cobertura total del plan.

## 15. Semántica de errores

### 15.1.

Las solicitudes mal formadas DEBEN devolver error de validación de request.

### 15.2.

Las solicitudes sintácticamente válidas pero semánticamente inviables DEBEN devolver error de negocio apropiado.

### 15.3.

Las transiciones de estado inválidas DEBEN rechazarse explícitamente y NO DEBEN reinterpretarse silenciosamente.

### 15.4.

La inexistencia de `process_id` DEBE distinguirse de la invalidez de transición.

### 15.5.

`FAILED` y `STOPPED` DEBEN ser distinguibles causalmente tanto en `status` como en la información terminal expuesta.

## 16. Reglas de consistencia observable

### 16.1.

`Get Process Status` y `Get Process Results` DEBEN ser consistentes entre sí respecto de:

* estado del proceso;
* tipo de resultado;
* terminalidad.

### 16.2.

Un proceso NO DEBE exponer `FINAL` mientras su estado observable no sea `COMPLETED`.

### 16.3.

Un proceso terminal DEBE exponer información terminal no nula.

### 16.4.

Un proceso no terminal NO DEBE exponer información terminal.

## 17. Compatibilidad con el challenge base

Este RFC se mantiene compatible con el challenge en los siguientes puntos:

* conserva el modelo de procesamiento asíncrono y observable por API;
* conserva el procesamiento batch de archivos `.txt`;
* conserva persistencia de estados, resultados y logs;
* conserva el conjunto de estados exigido;
* conserva las operaciones de start, stop, status, list y results. 

Las extensiones conscientes introducidas por este RFC son:

1. autorización explícita para dar semántica real a `PENDING`;
2. operacionalización plena de `PAUSED` mediante `pause/resume`;
3. formalización de la semántica de resultados `NONE / PARTIAL / FINAL`;
4. formalización de la evidencia documental como base del agregado.

## 18. Notas de cumplimiento

Una implementación conforme a este RFC DEBE demostrar, como mínimo:

* creación válida de proceso en `PENDING`;
* transición válida `PENDING -> RUNNING`;
* pausa y reanudación válidas;
* detención válida sin colapso a `FAILED`;
* exposición correcta de `NONE`, `PARTIAL` y `FINAL`;
* rechazo explícito de transiciones inválidas;
* consistencia entre status, progreso y resultados.

## 19. Open questions

Este RFC deja deliberadamente abiertas, para PDR/ADR posteriores, las siguientes cuestiones:

* granularidad exacta del checkpoint seguro para `pause/stop`;
* política definitiva de fallos parciales (`FAIL_FAST` vs tolerancia parcial);
* representación persistente concreta de snapshots;
* tecnología y modelo de ejecución asíncrona;
* estructura física del detalle documental y del log de actividad.

## 20. Dictamen

Este RFC queda propuesto como **source of truth normativo** para el lifecycle y la semántica externa del servicio.
